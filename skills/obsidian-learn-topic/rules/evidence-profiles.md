# Evidence profiles

每个单元必须选择一个主 `evidence_profile`。允许记录辅助证据，但毕业判断只围绕主能力，避免把所有内容塞进同一套题型。

| Profile | 适用目标 | 最低独立证据 | 迁移证据 |
| --- | --- | --- | --- |
| `concept-explanation` | 解释概念或机制 | 用自己的话解释因果链，并纠正一个错误心智模型 | 解释新场景中的相同机制 |
| `tutorial-reproduction` | 跟随教程构建结果 | 独立复现并有意修改贯穿案例 | 在不同输入或约束下重建 |
| `task-operation` | 完成真实操作 | 在确认环境中完成任务并核验结果 | 面对变化条件仍能完成 |
| `reference-application` | 查找和应用参考信息 | 找到正确条目并用于解决问题 | 在陌生参数或版本中正确定位 |
| `code-practice` | 编写或修改代码 | 用户真实尝试通过公开测试，并解释关键边界 | 新变式或不同约束下独立通过 |
| `repository-reading` | 读懂仓库 | 从入口追踪一条真实调用链并以源码证据说明 | 追踪另一条关联链路 |
| `repository-patch` | 修改仓库 | 固定 Commit 上的非空最小 Patch 与相关测试通过 | 在新边界条件下修正并保持回归 |
| `custom` | 上述类型不能准确表达 | 路线图明确写出可观察结果、证据来源与失败条件 | 路线图明确写出新场景要求 |

## 选择规则

- 一个单元只有一个主 profile；如果两个成果可分别验收，应拆成两个单元。
- profile 在路线确认后不能静默改变；变更需更新路线图权威契约，并说明对既有证据的影响。
- `custom` 不是兜底空值，必须公开毕业条件。
- 证据来源标记为 `host-tool`、`user-ci` 或 `user-supplied`。只有前两者，或经独立复核的用户证据，能单独支持毕业。
