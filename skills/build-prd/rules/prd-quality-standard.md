# 产品需求包质量标准

字段格式、编号、表格列、清单字段、目录结构、版本格式与行为样例 kind 枚举由 `scripts/validate_prd.py --strict` 与 `templates/` 强制，本文件只保留脚本无法判断的语义原则。

## 1. 事实、决策与证据

每个结论必须来自至少一种可说明的依据：实际验证的产品行为、用户可见文档或测试、用户明确确认的目标决策、已确认采用的外部实践。

代码只能证明实现线索，不能自动证明产品意图。现状、文档和目标冲突时先让用户选择。正式包不使用“可能”“建议考虑”掩盖未决问题，也不保留 TODO、TBD、假设、开放问题或待确认项。

## 2. 正式内容与过程内容

正式需求包记录最终产品事实、已确认决策、必要设计依据和可复核样例。以下内容只属于过程检查点或当前对话，不进入正式包：访谈逐字稿和问题顺序；模型推理、工具调用、失败尝试和临时猜测；旧项目内部架构、技术栈、模块、数据库、内部 API 与代码组织；工程任务、部署步骤、排期、预算和组织分工。

过程检查点固定在 `.build-goals/build-prd/`，不得被当作可实施需求。

## 3. 真实样例与脱敏

用户输入样例必须是真实值、代表性强且不含敏感数据，保存真正交给产品的值（可以为空字符串、`null`、数组或对象）。不要写“一个正好 80 字符的输入”代替真实 80 字符数据，也不要写“空值”代替实际空值。涉及敏感数据时使用不改变行为含义的脱敏样例，并标记 `sensitive_data=sanitized`。

每项功能至少记录一个典型正常样例（`normal`）。只有需求或已验证产品事实中确实存在相应行为时，才增加信息不足追问（`clarification`）、无效或不适用（`invalid`/`not_applicable`）或边界（`boundary`）样例。

## 4. 对外契约与实现自由

需求包只记录用户或外部系统已经依赖的命令、路径、格式、公开 API、文件结构、错误码和兼容规则。是否保持或改变这些行为由用户目标和已确认迁移范围决定；不得把旧行为默认写成兼容要求。新项目可以重新设计框架、模块、数据库和内部流程。

## 5. 调研只作候选

调研范围由当前产品决策决定，只读取能够改变方案选择的一手来源，并记录名称、URL、访问日期和具体借鉴点。外部实践只能成为候选方案，用户确认后才能写成产品要求。

## 6. 产品质量与验收

只写需求或已验证产品事实支持、且用户可观察和可重复检查的结果；不为了模板完整而补设反馈时间、角色权限、隐私、无障碍、兼容或失败恢复要求。Given/When/Then 中 Given 是用户可建立状态，When 是用户操作或可观察事件，Then 是唯一、具体、可检查的外部结果。
