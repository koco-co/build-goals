# 产品事实、外部实践与功能域地图

## 1. 识别来源

先读取用户已经提供的自然语言、路径和当前会话结论，不要求用户重新填写模板。

- 已有项目：以用户指定路径为来源项目；没有指定时才使用当前目录。
- 产品想法：从自然语言中提取产品作用、目标用户、核心场景、输入、输出、范围和限制。
- 已完成 `shape-idea`：复用同一主题的已确认结论，不重复询问。
- 已有需求包：先运行严格校验；未确认、文件哈希漂移或存在未决内容时不能直接沿用。

只有用户主动询问输入格式，或无法识别产品主题与来源时，才读取 `templates/prd-intake.template.md`。

## 2. 只读分析已有项目

按产品事实需要检查：

- 项目规则、README、用户文档、帮助与已有需求；
- 页面、路由、菜单、命令、提示词、文件入口和用户可见配置；
- 产品行为测试、示例、最终提示文案和错误恢复；
- 登录、引导、设置、权限、搜索筛选、导入导出、通知、后台管理与运营入口；
- 用户实际提供的输入，以及产品生成的页面、文本、结构化数据、文件或外部可观察动作；
- 用户或外部系统已经依赖的命令、路径、字段、格式、公开 API 和文件契约；
- Git 状态，用于识别并保护已有修改。

代码和测试只用于证明产品行为与外部契约。不要把框架、模块、数据库、内部数据模型、服务划分或实现流程带入需求包。

可以在没有外部副作用时安全运行产品流程，并记录事实证据。不得创建真实订单、发送真实消息、修改生产数据或执行其他未授权动作。无法安全运行的行为必须由现有可复核证据或用户确认确定，不能静默推断。

## 3. 梳理产品想法

产品想法至少需要形成：

- 产品解决的问题、目标用户与角色；
- 用户进入、操作、恢复和离开的完整路径；
- 用户会提供的内容、文件、字段、选项或上下文；
- 产品应返回的内容、呈现形式、固定结构、语义要求和运行时可变信息；
- 必须包含、明确排除和用户可感知的质量要求。

信息不足时先形成待决策清单，不提前编写正式需求文件。

## 4. 执行联网调研

每次正式生成或更新需求包，最低覆盖：

- 2 个直接或相邻竞品的公开产品流程；
- 2 个仍活跃的相关开源项目；
- 适用的官方产品、交互、无障碍或行业规范。

优先读取官网、官方帮助、官方演示、官方文档和源码仓库等一手来源；记录名称、URL、访问日期与具体借鉴点。核对维护状态和适用版本，比较输入、输出、交互、异常恢复、兼容契约与无障碍做法。

外部实践只能成为候选方案。任何会改变产品范围、输入、输出、交互、文案或验收结果的内容，都必须转化为一个附带推荐答案的用户决策。

## 5. 建立功能域地图

按用户能够理解的业务能力划分功能域，不按代码目录或服务拆分。每个功能域至少记录：

- 稳定的小写连字符 ID 和中文名称；
- 作用、角色、入口、范围与明确排除；
- 主要用户输入和主要输出；
- 对其他功能域的直接依赖；
- 需要保持的外部契约。

将整张地图及推荐拆分一次性提交用户确认。此处只确认“分几块、每块负责什么、依赖什么”；不要提前询问域内所有细节。

用户确认后冻结功能域 ID、名称和依赖顺序。后续发现必须新增、合并或拆分功能域时，说明影响并重新确认地图；未变化的功能域不重复确认。

完成条件：可自行查明的事实已经查明，调研覆盖达标，功能域地图已确认，剩余内容都是逐域需要用户选择的真实产品决策。
