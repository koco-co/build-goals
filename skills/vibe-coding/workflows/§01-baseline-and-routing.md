# 基线建立与路线选择

## Phase 1: 保护当前工作

1. 记录：
   - 当前仓库绝对路径；
   - 当前分支与 HEAD SHA；
   - `git status --short`；
   - `git worktree list`；
   - 最近提交；
   - 已存在但未提交的文件和修改。
2. 将所有现有改动视为用户工作。只读取，不执行 reset、clean、stash、强制 checkout、历史改写或自动格式化全仓。
3. 如果目标目录不是 Git 仓库，记录这一事实；不要为了满足流程而擅自初始化 Git，除非任务方案明确包含初始化。
4. 如果发现并发 Agent、其他 worktree 或当前会话之外的提交，建立所有权表，避免重叠修改。

## Phase 2: 读取项目规则

按优先级读取：

1. 用户在当前会话给出的明确要求；
2. 仓库根目录及目标子目录中的 `AGENTS.md`、`CLAUDE.md`；
3. README、CONTRIBUTING、docs、ADR、开发规范；
4. 包管理、构建、测试、Lint、类型检查和 CI 配置；
5. 安全、环境变量、数据库和部署说明。

记录规则来源和适用范围。规则冲突时不自行选择会改变结果的一方；在架构方案中说明推荐处理。

## Phase 3: 选择执行路线

### PRD 驱动路线

满足以下条件时进入：

- `docs/PRD需求文档.md` 存在；
- 文档状态已经确认；
- PRD 可以通过 `scripts/validate_prd.py` 严格校验；
- 用户目标是实现 PRD 中的产品。

提取全部 `F-NNN` 和 `F-NNN-AC-NN`，建立需求追踪基线。

PRD 缺失、未确认或校验失败时，转交 `build-prd`。不得用代码现状或用户零散描述替代权威 PRD。

### 已有项目迁移路线

满足以下任一条件时进入：

- 用户要求架构审查、最佳实践升级或现代化迁移；
- 项目能运行，但目录、依赖、测试、配置或开发体验明显低质量；
- 用户要求基于竞品、官方资料和开源项目提出目标架构。

迁移路线不要求先存在 PRD，但必须区分产品行为保持项、允许调整项和纯工程治理项。

## Phase 4: 形成基线摘要

摘要至少包含：

- 执行路线与原因；
- 当前 HEAD 和工作区状态；
- 用户现有改动及保护方式；
- 技术栈、入口、运行方式、测试和 CI；
- 输入文档及其验证状态；
- 可用 Agent、worktree、浏览器和测试能力；
- 已知限制与阻塞；
- 下一阶段只读调研范围。

完成前不得修改项目。
