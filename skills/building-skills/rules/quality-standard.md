# Skill 质量标准

## 1. 实现优先级

按以下顺序选择最可靠的表达方式：

```text
仓库已有 CLI 或确定性工具
    ↓
可执行脚本与测试
    ↓
结构化模板
    ↓
Few-shot 示例
    ↓
简洁规则
    ↓
说明性提示词
```

不得用冗长提示词重复代码已经能够保证的行为。

## 2. 单一规范源

- 每条规则、产物结构和平台行为只保留一个权威定义位置；
- 其他文件通过引用使用，不复制完整正文；
- 修改一个事实需要同步多处时，说明结构已经产生漂移风险；
- 平台适配只表达差异，不复制核心工作流。

## 3. 路由质量

Description 和 Routing 必须共同说明：

- Skill 做什么；
- 什么输入进入哪个分支；
- 什么时候不应使用；
- 任务超出范围时如何退出或转交；
- 显式调用与隐式调用策略。

相邻任务不能因为关键词相似而误触发。

## 4. 渐进式读取

- 初始上下文只加载 `SKILL.md`；
- 每个附属文件都有明确读取条件；
- 需要时完整读取相关文件，不靠零散片段猜测；
- 文件引用使用相对 Skill 根目录的路径；
- 避免深层链式引用，附属文件原则上不再要求读取大量其他文件。

## 5. 决策与确认

- 可自行查明的事实不询问用户；
- 已知答案不重复询问；
- 只有会改变实现或验收的真实决策才提问；
- 每轮一个主要问题，并给出推荐答案和影响；
- 用户确认设计前不得写入目标文件；
- 实施确认不自动包含提交、推送、发布或破坏性操作授权。

## 6. 内容质量

- 使用清晰、直接、可执行的语言；
- 每个步骤都有完成条件；
- 每个分支都有成功、失败或退出结果；
- Guardrails 保护真实数据、权限和接口风险；
- 一般行为用正向目标描述，安全红线使用明确禁止；
- 不保留 TODO、TBD、空白占位或无法验证的承诺；
- 示例必须值得模仿，不能只展示玩具片段。

## 7. 验证质量

完成标准至少包括：

- 结构与引用机械检查；
- 脚本或 CLI 的实际运行；
- 语义清单；
- 正向、负向和失败场景；
- 平台真实运行或明确的未验证说明；
- 修复后重跑受影响检查。

“看起来正确”和“文件已经生成”不属于验证证据。

## 8. 兼容与迁移

升级已有 Skill 时：

- 先识别稳定接口和外部依赖；
- 默认保留兼容行为；
- 破坏性调整必须说明影响、迁移方案和回退方式；
- 不以“重构”为由删除用户仍在依赖的能力；
- 变更范围必须与用户确认的设计一致。
