# 产品 PRD 质量标准

## 1. 事实与决策

PRD 中的每个结论必须来自以下至少一种依据：

- 已实际验证的项目产品行为；
- 项目现有产品文档、测试或用户可见内容；
- 用户在当前主题中明确确认的产品决策；
- 已由用户确认采用的外部最佳实践。

代码能够证明实现存在，但不能自动证明产品意图。实际行为、现有文档和目标决策冲突时，先提交给用户选择，再写入最终结论。

最终 PRD 不使用“可能”“建议考虑”“后续决定”等方式隐藏未决问题，也不保留 TODO、TBD、假设、开放问题、待确认项或阻塞项。

## 2. 产品内容边界

允许内容：

- 产品作用、目标用户、角色、场景和范围；
- 功能、入口、用户旅程、交互、状态和最终文案；
- 用户预输入、校验规则、正反示例和期望输出；
- 用户可感知的权限、隐私、无障碍、兼容、响应和恢复要求；
- 可观察、可重复执行的产品验收标准；
- 设计依据和公开来源。

禁止内容：

- 架构、技术栈、框架、库和技术选型；
- 数据库、内部数据模型、API 和服务接口；
- 部署、运维、工程任务、代码结构和实现步骤；
- 市场规模、商业计划、预算、排期和组织分工。

需要检查技术文件时，只提取产品事实，不能把技术细节转写进 PRD。

## 3. 调研质量

最低来源覆盖为 2 个竞品、2 个活跃开源项目和适用的官方规范。每条来源必须包含：

- 类型和名称；
- 可直接访问的一手 URL；
- 实际访问日期；
- 与当前产品相关的具体借鉴点。

通过近期发布记录、提交、发行版或维护说明确认开源项目仍活跃。来源存在冲突时比较适用场景，不按数量投票。调研结论先形成候选方案，只有用户确认后才能成为产品需求。

## 4. 文档结构

目标文件固定为 `docs/PRD需求文档.md`，并以 `# PRD需求文档` 为唯一主标题。

产品级章节提供理解所有功能所需的共同基准；功能详细设计承担具体行为。不得在不同章节复制同一套需求正文。

已有项目必须分别描述“已实现现状”和“目标需求”。产品想法没有既有实现时，应明确记录已经确认的起点事实，不编造现状。

## 5. 功能编号与覆盖

- 每项产品功能使用唯一且稳定的 `F-NNN` 编号；
- 更新现有 PRD 时沿用仍有效编号；
- 已废弃编号不重新分配给其他功能；
- 验收标准使用 `F-NNN-AC-NN`，并只能归属于对应功能；
- 功能地图中的每个功能都必须有详细设计，详细设计中的功能也必须出现在功能地图或用户旅程中。

“所有功能”覆盖前台、后台管理、登录引导、设置、权限、搜索筛选、导入导出、通知、命令或提示词入口，以及适用的空状态、异常和恢复流程。纯工程辅助能力不进入 PRD。

## 6. 用户预输入与期望输出

每项功能的用户预输入使用 Markdown 表格，至少包括：

- 字段或内容；
- 提供者；
- 必填性；
- 格式与范围；
- 默认值；
- 校验规则；
- 正确示例；
- 错误示例。

期望输出表格至少包括输出内容、呈现形式、触发条件、排序或状态、用户后续动作和完整示例。

只有产品本身要求 JSON、YAML、文件或提示词结构时，才在表格后补充相应完整示例；不得把用户输入输出写成内部 API 契约。

## 7. 交互状态与最终文案

所有用户可见内容必须提供可直接使用的最终文本及出现条件，覆盖适用的：

- 入口说明、字段标签和占位提示；
- 格式要求、按钮、确认和取消；
- 加载、空状态、成功和失败；
- 权限不足、危险操作和恢复路径。

不得使用“友好提示”“显示错误信息”“文案后定”等占位描述。错误反馈必须说明发生了什么以及用户下一步可以做什么。

## 8. 产品质量要求

只写用户可观察或可验收的结果，例如：

- 多久出现可理解的反馈；
- 哪些角色可以看到或执行某项能力；
- 用户数据如何被告知、确认或撤销；
- 键盘、读屏和焦点行为；
- 支持的用户环境和降级体验；
- 失败后保留什么输入以及如何恢复。

不规定缓存、数据库、服务、框架或部署方式。

## 9. 验收标准

每个主流程和适用分支都必须有验收标准。优先使用 Given/When/Then，确保：

- Given 是用户可建立的前置状态；
- When 是用户操作或可观察事件；
- Then 是唯一、具体、可检查的产品结果；
- 不把内部函数调用、数据表或服务状态作为验收结果；
- 最终文案、输入保留、焦点和后续动作在需要时进入 Then。

## 10. 单一事实源

目标目录只保留一份 `PRD需求文档.md`。更新时规范化同一文件，不追加相互冲突的历史版本，不生成备份、调研报告或额外 PRD。
