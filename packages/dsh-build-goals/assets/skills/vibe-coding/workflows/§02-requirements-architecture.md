# 需求包驱动的架构设计

适用于路线 1–3。

## 1. 建立需求与功能域矩阵

完整读取 `docs/产品需求/需求包清单.yaml` 和 `PRD需求文档.md`。先加载功能域索引，再按依赖顺序读取每个功能域的需求与行为样例。

为每个功能域记录：

- `F-NNN`、验收 ID 和行为样例 ID；
- 用户角色、入口、实际输入、追问、状态和输出；
- 输出固定结构、语义要求和运行时可变内容；
- 必须保持的命令、路径、格式、公开 API、文件和兼容规则；
- 权限、响应、恢复、无障碍和安全要求；
- 直接依赖的输入输出契约。

默认只保持外部可观察行为，内部架构可以重新设计。需求包未明确要求的旧模块、框架或数据库不是不可变约束。

## 2. 按路线读取项目

- 路线 1：不读取旧项目，只读取目标目录中为保护用户工作所需的 Git 和规则事实。
- 路线 2：使用 `prompts/legacy-reference-inspector.agent.md` 派发独立只读 Agent，输入只包含用户授权路径与要回答的问题。返回结果必须是行为、输入、输出、公开契约、证据和证据缺口摘要；主 Agent 不把旧项目代码或架构原样注入架构讨论。
- 路线 3：读取当前项目的实现、测试、配置和文档，建立“已满足 / 缺失 / 冲突 / 明确变更”矩阵；现有实现仍不是产品意图的自动来源。

没有 Subagent 能力时由主 Agent 串行执行同样的读取边界，在方案中明确“只读参考由主 Agent 降级完成”。

## 3. 并行只读调研

平台支持时按需调用 Architecture Researcher、Competitor Researcher、Test Engineer 和 Security Reviewer。优先读取官方一手来源，记录访问日期、版本与维护状态。

研究 Agent 不写文件、不安装依赖、不运行有副作用的命令，也不替用户做产品取舍。

## 4. 形成候选方案

至少提出两个可行方案，比较系统边界、技术栈、目录与模块、数据和接口、用户界面或 CLI、测试、安全、配置、可观测性、部署、扩展成本和风险。

全局方案说明共同技术与跨域依赖；每个功能域说明本域边界、组件、接口和验证策略。大项目不把所有域细节塞进一个文档。

推荐方案必须覆盖：

1. 一句话结论与项目路线；
2. 需求快照及旧项目参考边界；
3. 采用和拒绝的关键技术；
4. 完整目录树与依赖方向；
5. 跨域及逐域接口、数据和输出契约；
6. 环境、秘密、测试数据和安全；
7. TDD、CI、E2E、视觉与无障碍策略；
8. 从当前基线到可运行系统的阶段顺序；
9. 风险、停止条件与回退。

## 5. 第一次全局确认

只在对话中展示推荐架构和备选差异，请用户一次确认架构、技术栈、目录、跨域边界、旧项目参考范围、兼容与部署边界、明确排除项。

确认前不创建 `docs/架构设计/`，不搭建脚手架，不修改代码。功能域细节已经由需求包确认时不重复询问；发现真正缺失的产品决策时回到 `build-prd`，不在架构阶段猜测。
