# PRD 驱动架构设计

## Phase 1: 建立需求与约束矩阵

1. 完整读取 `docs/PRD需求文档.md`。
2. 为每个 `F-NNN` 和 `F-NNN-AC-NN` 记录：
   - 用户角色与入口；
   - 输入、输出和状态；
   - 数据、权限、性能、兼容和恢复要求；
   - 是否涉及前端、后端、任务、存储、外部服务或 Agent 能力。
3. 读取已有代码时区分“可复用资产”和“历史偶然实现”，不因为已有文件就默认沿用其架构。
4. 明确运行环境、部署边界、团队规模、维护周期和不可变约束。

## Phase 2: 并行只读调研

在平台支持时并行派发：

- `prompts/architecture-researcher.agent.md`：官方规范、当前稳定技术栈和工程工具；
- `prompts/competitor-researcher.agent.md`：竞品实现模式与活跃开源项目；
- `prompts/test-engineer.agent.md`：测试策略、可测试性和测试数据；
- `prompts/security-reviewer.agent.md`：身份、权限、秘密、数据流和供应链风险。

研究 Agent 只读，不创建文件、不安装依赖、不运行有副作用的命令。

优先使用一手来源。对版本、维护状态和生态活跃度记录访问日期；不要把搜索热度等同于技术适配度。

## Phase 3: 形成候选方案

至少形成两个可行方案。每个方案说明：

- 系统边界与部署形态；
- 核心技术选型及当前稳定版本策略；
- 目录树与模块职责；
- 数据模型、接口和事件契约；
- 前端设计系统或 CLI 交互层；
- 测试、可观测性、安全、配置和运维；
- 扩展路径、迁移成本和主要风险；
- 满足需求追踪矩阵的方式。

使用加权决策矩阵比较可维护性、可读性、扩展性、可测试性、交付速度、生态成熟度、迁移成本和运行成本。

## Phase 4: 推荐方案

推荐方案必须包含：

1. 一句话架构结论；
2. 采用与不采用的关键技术；
3. 完整目标目录树；
4. 组件、模块和依赖方向；
5. 输入、输出、API、事件与数据契约；
6. 环境变量与秘密管理；
7. 正常测试数据和隔离环境策略；
8. TDD、CI、E2E 和可选视觉验证策略；
9. 主要 ADR 决策与权衡；
10. 从空仓库或现有骨架到可运行系统的阶段顺序。

所有决策必须能够追溯到 PRD、项目约束或调研证据。

## Phase 5: 用户确认门禁

只在对话中展示推荐方案和备选差异。询问一次是否确认：

- 推荐架构；
- 技术栈；
- 目录与模块边界；
- 兼容性和部署边界；
- 明确排除项。

用户确认前不创建 `docs/架构设计方案.md`，不搭建脚手架，不修改代码。
