# 现有项目架构或技术栈迁移

开始前保持 `baseline_readonly`。迁移审查必须先形成独立 Findings，再由架构方案引用，不能拿生成后的架构文档反向证明审查完整性。

## Phase 1：全仓盘点

使用角色提示文件 `prompts/repository-auditor.agent.md` 分区审查，保持只读。按其中的 Audit Areas 逐区审查；每条 Finding 的证据字段、严重度与秘密处理以 `rules/repository-audit.md` 为准。

每个发现先在审查结果中分配稳定的 `AUD-NNN`，记录文件证据、影响、严重度、建议和可验证条件，不用个人偏好替代缺陷证据。Finding 必须来自旧项目或外部事实本身，不能引用尚未生成的迁移架构作为证据。

同时单独建立外部行为基线：用户实际输入、输出语义，以及真实存在的固定结构、命令、路径、格式、公开 API、文件、错误行为和跨功能旅程。哪些行为保持或改变，以用户确认的迁移目标为准。

第一次全局架构确认前，Findings 只在对话中展示并保持目标项目只读。用户确认推荐架构方案后进入 `architecture_approved`，先使用 `templates/migration-findings.template.yaml` 将已展示的审查结果写入 `docs/架构迁移/审查发现.yaml`，再写迁移架构文档。后续任务与交付追踪以该独立文件中的 `AUD-NNN` 为权威审查输入。

## Phase 2：外部参考调研

按迁移决策需要调用：

- `prompts/architecture-researcher.agent.md`；
- `prompts/competitor-researcher.agent.md`；
- 涉及明确安全边界时使用 `prompts/security-reviewer.agent.md`；
- 需要独立测试方案时使用 `prompts/test-engineer.agent.md`。

调研当前官方推荐、同类成熟产品、活跃开源项目和该技术生态的现代化工程实践。明确可直接借鉴、需要适配和不适合本项目的部分。

## Phase 3：当前与目标架构比较

建立差距矩阵：

| 领域 | 当前证据 | 风险或成本 | 目标状态 | 迁移方式 | 验证 |
| ---- | -------- | ---------- | -------- | -------- | ---- |

只覆盖当前迁移实际涉及的领域，例如目录和模块、工具链、数据和接口、验证、配置、文档与 Agent 指令、构建或部署、UI、兼容与回滚。

区分：必须修复、推荐改进、暂不处理、需要产品决策。每个需要实施的差距必须引用一个或多个 `AUD-NNN`；纯目标设计不得新造 Finding 来证明自身必要。

## Phase 4：迁移方案

提出真实可行的迁移策略；只有一个可行策略时说明排除其他策略的事实依据。推荐方案只说明本次迁移实际涉及的内容：

- 迁移边界和不回滚的现有用户工作；
- 保持不变的产品行为和稳定接口；
- 目标目录树和依赖方向；
- 已确认的数据、配置、环境变量和秘密迁移；
- 需要更新的 AGENTS、CLAUDE、README 或忽略文件；
- 阶段顺序，以及实际需要的兼容、数据回滚与代码回滚；
- 每阶段可独立验证和提交的功能单元；
- 已证实风险对应的停止条件和恢复方式。

按用户可理解的功能域拆分迁移内容。全局迁移文档记录共同基线、目标架构、阶段和回滚；`docs/架构迁移/功能域/<功能域>.md` 记录本域边界、Findings、接口契约、验证和回退。

迁移改变前端、GUI、TUI 或 CLI 时，完整读取 `../rules/ui-interaction-preview.md`。按本次迁移影响的完整用户流程展示当前与目标可见状态，明确保留、删除和改变的操作；再补充目标技术状态流，包括前后端边界、数据迁移或写入、异步处理、失败回滚和模块调用。

## Phase 5：用户确认门禁

只在对话中展示独立审查摘要、候选方案和推荐迁移路径。存在 UI 变化时，同一次确认还要展示全部受影响可见状态和技术状态流。用户确认前：

- 不创建 `docs/架构迁移/`；
- 不批量格式化；
- 不升级依赖；
- 不移动目录；
- 不修改代码、配置或文档。

用户确认后，先落盘 `审查发现.yaml`，再生成引用这些 Findings 的架构文档；不得颠倒顺序或从架构文档反推 Findings。
