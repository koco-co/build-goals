# 当前资料调研策略

## 来源优先级

1. 官方文档、语言规范、标准和论文。
2. 官方或维护方仓库、发布记录、迁移指南和安全公告。
3. 官方课程、维护方示例和经过版本标注的参考实现。
4. 高质量技术课程、书籍或文章。
5. 官方 Issue/Discussion、维护者回复和可复现社区问题，用于踩坑与边界。

模型已有知识只用于生成检索方向，不作为动态版本、API、项目状态或“最佳实践”的证据。

## 两阶段调研

### 路线级广度调研

覆盖：

- 当前受维护版本、语言绑定和生命周期。
- 前置知识、环境和最低工具链。
- 核心概念、学习依赖和合理阶段顺序。
- 主要竞品、替代方案、适用与不适用场景。
- 常见失败模式、迁移风险和安全边界。
- 可运行练习、官方示例、深入方向和面试关注点。

### 章前深度核验

每个知识单元创建前重新核验：

- 本章适用版本和发布日期。
- API、CLI、配置和代码示例。
- 已知问题、弃用项和迁移说明。
- 实践依赖与实际运行条件。

如果核验发现上游相对路线图中的 `version_baseline` 已变化，先把课程路线标记为 `changed`，列出受影响的单元、正文示例、练习和验收，再请求是否迁移。确认前继续固定旧基线或停止相关单元，不静默把新旧 API 混入同一路线。迁移完成后更新版本基线、核验日期、来源和迁移说明，并重新执行受影响验收。

### 框架与库的覆盖审计

对持续演进的语言、框架、工具链或库，章前核验还必须完成一份轻量覆盖清单：

1. 官方文档目录中的相关能力入口是否已归类到当前单元、后续单元或明确排除范围。
2. 当前语言绑定的 API/CLI 签名、参数和默认行为是否与示例一致；必要时用本地锁定版本做只读 introspection。
3. 每个必需目标是否都有“来源 → 正文 → 实践/测验证据”的闭环；只有导航中出现链接不算覆盖。
4. 旧 API、弃用项、浏览器/平台差异和安全边界是否单独标注版本范围。

覆盖审计不是要求一篇笔记塞入全部官方文档，而是要求每个遗漏都有明确归属，避免在用户追问后才临时发现基础分类缺口。

## 完成条件

路线级调研只有在版本、前置、核心概念、学习顺序、环境、替代方案、踩坑、深入方向和实践资源均有可靠来源，且主要来源冲突已解释时完成。

以下情况阻断路线创建：

- 官方文档、规范、官方仓库或当前版本信息无法访问。
- 无法判断目标版本或语言绑定是否仍受维护。
- 关键前置或安全边界只有无来源二手说法。

一手资料充分但部分课程或社区材料不可用时可以继续，并把缺口标为待补充。

## 时效判断

- `verified_at` 缺失或过久只触发复核，不直接判废。
- `version_scope` 与学习目标不一致时，判断保留旧版本价值。
- 只有官方变更、API 移除、项目停更、链接失效、示例不可运行或当前实现冲突等证据才能判定过时。
- 动态事实写入核验日期和适用版本；无法核验时使用 `status: 待核验`。
- 路线图同时保存 `version_baseline`、`source_checked_at` 与 `upstream_status`；单篇正文保存自身 `version_scope` 与 `verified_at`，两层信息不得互相冒充。

## 踩坑证据

- 优先使用官方 FAQ、故障排查、迁移文档和维护者确认的 Issue。
- 社区经验必须给出来源、复现条件和版本范围。
- 区分普遍缺陷、版本特定问题、配置错误和个人偏好。
- 不把单个帖子概括成所有用户都会遇到的问题。

## 开源仓库分支

学习 GitHub 开源仓库时完整读取 `rules/repository-learning-policy.md`。路线级调研额外核验仓库归属、完整 Commit、许可证、默认分支、发布与维护状态、构建/测试入口、核心模块和安全边界；README 只作为入口，关键结论必须回到固定 Commit 的源码、测试、Issue/PR 或发布记录。
