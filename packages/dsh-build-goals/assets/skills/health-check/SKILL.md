# Outcome

把 build-goals 对项目结构与规范产物的要求封装为一个入口：先只读检查并一次性报告真实问题，用户确认后直接组织修复、验证并重新运行健康检查。

## Routing

- 用户要求检查项目结构、规范产物或项目健康状态时，执行独立检查分支。
- 由 `vibe-coding` 等上层总控受控调用时，按上层指定的基线、就绪或最终交付检查点限定适用范围；没有发现问题时直接返回，不增加用户交互。
- 发现问题时先报告证据、修复方案、影响文件和验证方式；用户确认前保持只读，确认后进入修复分支。
- 本 Skill 只随完整 `build-goals` Plugin 分发，不支持独立安装；内部领域能力由同一 Plugin 中的配套 Skill 提供。
- 代码质量、安全、依赖、测试覆盖率、CI 和性能审计不属于本 Skill。

## Steps

1. 建立检查范围
   - 完整读取 `rules/domain-contract.md` 和 `workflows/§01-inspection.md`。
   - 识别项目阶段、仓库形态、现有规范产物、工作区状态和上层总控提供的范围。
   - 对新项目的基线检查只检查当前阶段已经成立的前置条件，不把尚未到创建时点的产物报成问题。
   - 完成条件：本轮适用领域和明确排除项已有项目证据。

2. 执行只读领域检查
   - 按 `rules/domain-contract.md` 加载并受控调用适用的 `build-skill`、`build-plugin`、`build-readme`、`build-agents-md` 与 `build-prd` 审查分支。
   - Plugin 已包含的 Skills 由 Plugin 领域统一检查；Skill 领域只检查 Plugin 之外的独立或项目级 Skills，避免重复报告。
   - 子 Skill 只返回问题、证据、修复方案、影响文件和验证方式，不在检查阶段写入。
   - 完成条件：每个适用领域都有证据充分的问题或“未发现问题”结论。

3. 汇总并请求一次修复确认
   - 使用 `templates/health-check-report.template.md` 在对话中输出一次性报告，不创建报告文件。
   - 没有发现问题时直接交付检查范围与结论，不请求确认。
   - 发现问题时只请求一次修复确认；确认范围覆盖报告中列出的全部修复，不把内部 Skill 选择抛给用户。
   - 完成条件：无问题时已结束；有问题时用户已确认全部或明确的部分修复范围。

4. 修复、验证并复检
   - 用户确认后完整读取 `workflows/§02-remediation.md`。
   - 将每个已确认问题交回对应领域 Skill，按其现有写入、内容确认和验证契约修复；未确认的问题保持不变。
   - 运行领域校验与项目适用检查，然后重新运行健康检查。
   - 完成条件：已确认问题已修复并复检，失败、未验证或仍未确认的问题准确保留。

5. 交付
   - 完整读取 `checklists/semantic-acceptance.md`。
   - 独立调用时报告检查范围、已修复内容、验证证据和剩余问题；受控调用时把相同结果与恢复条件返回上层总控。
   - commit、push、发布、部署或本地 Plugin 更新不由本 Skill 自动执行。

## Delivery

- 首次检查只在对话中给出范围、问题、证据、修复方案、影响文件和验证方式。
- 修复后给出已修复项、实际验证命令与结果、复检结论，以及仍未修复或未验证的内容。
- `vibe-coding` 受控调用只记录 `health-check` 的检查点与结果，不向项目文档展开内部配套 Skill 清单。

## Guardrails

- 检查阶段保持只读；用户确认问题修复前，不创建、修改、移动或删除项目文件。
- 只报告有仓库事实、平台契约、可复现缺陷或用户明确要求支持的问题，不制造假想问题。
- 子 Skill 尚未展示的完整正文、产品行为或公开契约仍按其自身确认门禁处理；上层修复确认不替代这些内容决策。
- 保护用户未提交修改、并发工作、凭据、隐私数据和外部服务状态。
- 不创建持久化健康报告，不引入新的 Hook、MCP、脚本、CI 或项目级辅助目录。
- 不自动 commit、push、发布、部署或更新本地 Plugin。
