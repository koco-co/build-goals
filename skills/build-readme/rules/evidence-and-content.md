# README 事实与内容规则

## 1. 证据优先级

按以下顺序判断项目事实：

```text
实际代码、Manifest、Schema 和公开接口
→ 测试、CI 与可执行帮助命令
→ 当前配置示例与维护中的项目文档
→ 现有 README
→ Git 历史或合理推断
```

来源冲突时使用更接近当前运行实现的证据，并在预览中指出冲突。README 是需要保留的重要输入，但不是覆盖代码事实的唯一来源。

## 2. 项目定位和功能

- 一句话定位说明项目为谁解决什么问题，不使用“最佳”“完整”“生产级”等无证据宣传。
- 功能列表只包含当前可用能力；计划、实验和未验证能力必须显式标注。
- 对插件、SDK、CLI、应用和库分别说明真实使用入口，不混淆客户端、模型、协议和项目版本。
- 静态发现、单元测试、隔离安装和真实业务流程分开描述。

## 3. 安装、使用和配置

- 命令来自当前仓库，参数、路径和包名必须核对。
- 快速开始应给出从安装到首次成功使用的最少必要步骤；不要把完整开发环境搭建塞入首个示例。
- 不在 README 中暴露密钥、Cookie、令牌、内部地址或本机绝对路径。
- 对必需的环境变量使用占位名称和 `.example` 文件，不写真实值。
- 不能安全运行的命令只做静态核对，并标记未执行。

## 4. 测试、兼容性和许可证

- 只有实际运行完整声明范围后才能写“全部测试通过”。
- 版本、平台和运行时要求以 Manifest、锁文件、CI 或当前官方契约为准。
- 仓库没有许可证时明确写“尚未声明”，不得根据代码风格猜测许可证。
- 不虚构贡献者、采用者、下载量、Star、覆盖率或安全认证。

## 5. 内容取舍

- README 先服务首次访问者，详细内部规范保留在 `docs/` 并以链接引用。
- 每个章节必须帮助读者理解、安装、使用、验证或参与项目；否则省略。
- 已由自动生成文档、API Reference 或其他唯一规范源维护的长内容不复制进 README。
- 表格和图表只表达稳定关系，避免把频繁变化的文件清单固化为难维护插图。

## 6. 更新与多语言同步

- 更新前识别现有稳定标题、链接、锚点和外部引用，默认保持兼容。
- 对删除或重命名章节说明理由，必要时保留旧锚点。
- 仅同步实际存在并已列入预览的伴随 README。
- 多语言文件共享事实、命令和版本；表达可以本地化，不要求机械逐句对应。
