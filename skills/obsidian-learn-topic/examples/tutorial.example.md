# 教程样例：把脆弱选择器改成语义 Locator

> [!abstract] 学习成果
> 完成后，读者能把一条依赖页面结构的选择器改成表达用户意图的 Locator，并用公开测试验证结果。

## 开始前确认

读者已经能运行一条最小 Playwright 测试，并知道按钮在页面上具有可访问名称。本教程不负责系统解释自动等待；该机制应链接到独立原理正文。

## 贯穿案例

页面上有一个显示“提交订单”的按钮。旧测试用第三个 `button` 的位置定位它；页面插入新按钮后，测试点击了错误目标。

### 第一步：写出用户实际看到的目标

用户不是在寻找“第三个按钮”，而是在寻找名为“提交订单”的按钮。先把意图写成一句自然语言，再选择能表达角色和名称的 Locator。

### 第二步：替换并保留唯一断言

```python
submit = page.get_by_role("button", name="提交订单")
expect(submit).to_be_visible()
submit.click()
```

这里的可见断言证明操作前提；业务结果仍需要由下一条业务断言验证。

### 完整结果

测试不再依赖按钮在 DOM 中的顺序。若页面同时出现两个同名按钮，严格性错误会暴露语义仍不够唯一，而不是随机选择一个目标。

## 阶段检查

- Locator 是否表达用户能感知的角色与名称？
- 页面结构变化但用户意图不变时，测试是否仍成立？
- Locator 不唯一时，失败是否提供了可诊断信号？

## 为什么这样做

选择器稳定性来自“用户意图是否稳定”，不是字符串是否短。角色和可访问名称把测试与交互语义对齐，但不能替代页面本身正确的可访问性实现。

## 边界、失败表现与排错

- 同名目标确实有多个：增加能代表真实业务边界的容器或上下文。
- 名称来自动态内容：先确认稳定的业务标识，不把本地化文案假定为永远不变。
- 页面没有合理语义：优先修复产品标记；测试 ID 是受控兜底，不是默认首选。

## 独立练习

把另一个依赖 CSS 层级的表单提交测试改为语义 Locator，并说明新 Locator 的用户意图、唯一性来源和一个仍可能失败的边界。
