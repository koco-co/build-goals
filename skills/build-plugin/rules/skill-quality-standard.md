# Skill 质量标准

## 最高优先级

禁止防御性编程和防御性提示词。行为、分支、兜底、兼容、校验、权限门禁、提示词和流程必须由用户需求、仓库事实、平台契约、可复现缺陷或明确安全要求支持；没有依据就不添加。必要的输入校验、数据安全、权限边界和错误处理不受禁止，但必须说明依据。

## 1. 实现优先级

按以下顺序选择最可靠的表达方式：

```text
仓库已有 CLI 或确定性工具
    ↓
可随目标交付的 .agents/scripts/ 共享脚本
    ↓
Skill 自有脚本与测试
    ↓
结构化模板
    ↓
样本示例
    ↓
简洁规则
    ↓
说明性提示词
```

- **脚本优先**：能够由脚本确定性保证的行为，不在提示词里重复堆规则。
- **共享有据**：只有多个 Skills 已有相同稳定契约，并且 `.agents/scripts/` 会随项目或整体安装包交付时，才把脚本提升为项目公共能力；不能保证共享目录存在时保持 Skill 自包含。
- **运行时从简**：新增脚本优先使用无需第三方依赖即可执行的 MJS 或 Shell；任务不适合时使用 Python 等语言，并把必要运行时、第三方依赖和可复现命令写入设计与验收。
- **模板与示例按需使用**：固定输出结构用模板；复杂、主观且容易误解的行为用高质量示例；简单约束使用简洁规则，不为凑示例而增加文件。
- **反冗长**：删除与脚本、模板、示例或规则文件重复的句子；同一约束只保留一处权威定义。

## 2. 单一规范源

- 每条规则、产物结构和平台行为只保留一处权威定义；
- 其他文件通过引用复用，不复制完整正文；
- 一项规则若需要同步修改多处，说明结构存在漂移风险；
- 平台适配只描述差异，不复制核心工作流。

## 3. 平台中立

- 正文默认使用平台中立的目标、步骤和交付语言，不为同一流程复制多套平台文案；
- 调用权限、展示信息和其他仅由配置决定的行为只写在 `SKILL.md` Frontmatter 与 `agents/openai.yaml`，正文不重复解释；
- 平台能力确实改变执行步骤、输出或降级方式时，正文可以保留最小条件分支，并写清无法等价实现时如何退出；
- 以平台配置或产物为工作对象的 Skill 可以按任务需要提及真实字段名、Manifest 和验证命令；
- 专业术语保持英文，统一拼写形态即可，不得强行中译。

## 4. 路由质量

`description` 和 Routing 必须共同说明：

- Skill 做什么；
- 什么输入进入哪个分支；
- 什么时候不应使用；
- 任务超出范围时如何退出或转交。

相邻任务不能因为关键词相似而误触发。

- 仅限用户调用的 Skill 由平台配置控制，不在正文重复说明调用权限；
- 允许模型调用的 Skill 优先在跨平台 `description` 中写明触发条件、排除条件，以及与相邻 Skill 的区别；
- 只有明确面向 Claude Code 且确有必要时才补充 `when_to_use`，不得让双平台 Skill 的唯一触发语义依赖该字段。

## 5. Frontmatter

- 按当前 Skill 提供的 Frontmatter 设计规则形成字段决策矩阵；
- 即使已有 Skill 只有 `name` 和 `description`，也要重新评估调用、参数、权限、上下文和环境要求；
- 可选字段必须有真实消费方或行为依据，不为形式完整统一补齐；
- `compatibility` 默认省略，只描述硬性环境要求；
- 平台专属字段必须由安装过程隔离，不能直接假定另一平台支持。

## 6. 渐进式加载

- 初始上下文只加载 `SKILL.md`；
- 每个附属文件都有明确读取条件；
- 需要时完整读取相关文件，不靠零散片段猜测；
- Skill 附属文件引用使用相对 Skill 根目录的路径；项目公共脚本使用项目根目录 `.agents/scripts/<script>` 调用命令，并且仅在交付过程保证该目录存在时使用；
- 避免深层链式引用，附属文件原则上不再要求读取大量其他文件。

## 7. 决策与确认

- 可自行查明的事实不得询问用户；
- 已知答案不得重复询问；
- 只有会改变实现或验收的真实决策才提问；
- 每轮一个主要问题，并给出推荐答案和影响；
- 用户确认设计前不得写入目标文件；
- 实施确认不得自动包含提交、推送、发布或破坏性操作授权。

## 8. 内容标准

- 内容审查回答“行为是否正确、完整”，不承担单纯的措辞美化；
- 每个步骤都有清楚的条件、动作、结果和完成证据；
- 已确认分支和可复现失败都有明确结果；没有证据的失败场景不补写；
- Guardrails 保护真实数据、权限和接口风险；
- 不得保留 TODO、TBD、空白占位或无法验证的承诺；
- 示例必须值得模仿，不得仅展示玩具片段；
- 内容存在歧义时先解决行为决策，不把猜测留给文案审查。

## 9. 文案标准

- 文案审查回答“是否自然、清楚、简洁并容易执行”，不得改变行为、范围、权限或验收标准；
- 使用日常、直接的语言，避免生硬翻译、抽象黑话和无必要术语；
- 相同概念使用同一名称，标题直接说明章节用途；
- 一般行为用正向目标描述，安全与权限红线使用明确禁止；
- 删除不改变理解、执行或验收结果的句子；
- 需要改写参考时读取当前 Skill 提供的文案审查示例；
- 文案修改完成后重新执行内容回归和受影响检查。

## 10. 独立审查

- 新建 Skill、整体重构，或改变触发、Frontmatter、权限与平台行为时，必须调用独立 Reviewer；
- Reviewer 只报告内容问题和文案问题，不修改文件；
- 主 Agent 修复后提交 Reviewer 复查；
- 微小且不改变语义的修改可以省略独立审查；
- 平台不支持独立 Agent 时执行主 Agent 审查，并在交付中标记“未完成独立审查”。

## 11. 验收标准

完成标准至少包括：

- 结构与引用静态检查；
- 脚本或 CLI 的实际运行；
- 内容审查、文案审查和文案修改后的内容回归；
- 适用时完成独立 Reviewer 审查；
- 已确认的应处理、不应处理和可复现失败场景；
- 平台真实运行或明确的未验证说明；
- 修复后重跑受影响检查。

“看起来正确”和“文件已生成”不属于验证证据。

## 12. 兼容与迁移

升级已有 Skill 时：

- 先识别稳定接口和外部依赖；
- 只保留已确认仍有调用方依赖的兼容行为；
- 破坏性调整必须说明影响、迁移方案和回退方式；
- 不得以“重构”为由删除用户仍在依赖的能力；
- 变更范围必须与用户确认的设计一致。
