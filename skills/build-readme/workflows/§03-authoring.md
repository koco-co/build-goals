# README 编写与同步

本阶段只执行用户明确请求或已确认的内容与文件范围。

## Phase 1：核对文件现状与修改范围

1. 重新读取目标 README 和 `git diff`，检查研究或预览后是否出现并行修改。
2. 将用户明确请求或已确认的新增、修改和删除路径作为本阶段的文件范围。
3. 保存准备保留的事实、链接、命令和用户文案清单。

出现无法自动合并的重叠修改时，停止并说明冲突，不用旧快照覆盖新内容。

## Phase 2：组织内容

按照读者完成任务的顺序编排：

```text
项目是什么
→ 为什么有用
→ 能做什么
→ 如何安装
→ 如何完成首次成功
→ 如何继续配置和验证
→ 有哪些限制、兼容性与许可证条件
```

更新已有 README 时优先保留有效事实与稳定链接，允许重组但不无理由丢弃历史信息。新建 README 时只写仓库能证明的章节。

## Phase 3：应用视觉系统

完整遵循 `rules/github-style.md`；视觉组件只按该规则和实际信息价值取舍，不在此重复视觉规范。

Markdown 标题默认使用 GitHub 生成的锚点；只有现有外部链接要求保持旧锚点时才添加显式锚点。图片必须有有意义的替代文本，优先使用仓库内资源。

## Phase 4：可选图片生成

只有用户明确授权生成图片且当前客户端确实提供该能力时才执行：

1. 根据项目真实定位编写具体视觉说明；
2. 使用项目已有资源目录，缺少约定时使用 `assets/readme/`；
3. 生成后实际查看图片，检查文字、裁切、透明背景、明暗主题和与项目事实的一致性；
4. 不满意时迭代，不把未检查的图片加入 README；
5. 记录这是生成资源，不虚构第三方作者或许可证。

没有图片生成能力时跳过并标为未使用，不用占位图或外部随机图片替代。

## Phase 5：同步伴随 README

只同步探索阶段已经发现且属于用户明确请求或已确认范围的文件：

- 共享功能、命令、版本、兼容性和限制保持一致；
- 保留各语言自然表达，不做机械逐句翻译；
- 不新建未获授权的语言版本；
- 验证所有伴随 README 的本地链接和资源路径。

完成条件：授权范围内的文件已经写入，内容有证据，视觉组件有信息价值，未触碰项目代码或未授权文件。
