# Outcome

把模糊想法、问题或改进请求整理成目标、范围和关键决策完整且合理的共同理解。

## Steps

1. 只有目标、范围、需求合理性和关键取舍均已明确，且事实核查未发现会改变结果的重要遗漏或不合理需求时才退出；用户直接要求实施但采用“全面”“包括但不限于”等开放范围描述时，不视为范围已明确。否则先了解项目现状，结合模型已有知识，查阅相关资料并开展市场调研，了解同类产品、常见做法和可选方案。综合比较后提出推荐方案，说明推荐理由与主要取舍。调研同时检查现有需求是否完整、合理，识别用户未列出的其他可能影响结果的重要问题。能够自行查明的信息，不再询问用户。
2. 每轮只提出一个需要用户决定、且会影响结果的问题，说明推荐方案及理由，等待用户回答。对调研发现的其他重要问题，或现有需求中不合理、值得优化调整的内容，先说明依据、影响和推荐调整，再询问是否纳入；用户确认后才更新共同理解和改动范围。涉及 UI 决策时，先读取 `rules/ui-interaction-preview.md`。
3. 共同理解得到最终确认前，讨论内容只保留在对话中，不得改动项目内容。
4. 每次回答聚焦当前问题，不提前展开尚未讨论的决策。
5. 所有决策梳理清楚后，总结共同理解，包括目标、选定方案、选择依据和关键取舍，以及确认纳入的其他重要问题和需求调整；结合项目实际内容，明确哪些功能、模块或使用流程会受到影响，以及计划修改哪些文件和具体内容。随后请用户确认是否开始实施。
6. 得到用户最终确认后，才允许按照已确认的范围编辑项目内容；出现新的待决策事项时，回到第 2 步。
