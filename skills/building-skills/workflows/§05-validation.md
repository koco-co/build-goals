# 验证

验证分为机械检查、语义验收、场景验证和平台验证。任何一层都不能替代其他层。

## Phase 1：机械检查

优先运行目标仓库已有命令。没有等价能力时，使用本 Skill 的校验器：

```bash
python3 scripts/validate_skill.py /path/to/skill --profile portable --strict
```

根据目标平台选择：

```bash
python3 scripts/validate_skill.py /path/to/skill --profile claude --strict
python3 scripts/validate_skill.py /path/to/skill --profile codex --strict
```

至少检查：

- `SKILL.md` 和 Frontmatter；
- 名称、目录和描述约束；
- 核心章节和顺序；
- 按需读取引用是否存在且未越界；
- 工作流编号是否连续；
- 模板和示例命名；
- 空文件、不可读文件和异常路径；
- 平台专属字段是否出现在正确配置层；
- 脚本语法、退出码和错误信息；
- 项目现有测试、Lint 和 CI。

## Phase 2：设计落实审查

逐项执行 `checklists/design-review.md`：

- 设计中的每个目标是否落地；
- 每个目录是否仍然必要；
- Hooks、CLI、脚本和 Skill 的职责是否正确；
- 是否出现重复规范源；
- 是否存在未经确认的范围扩张。

发现偏差时先修复设计或实现，再继续验证。

## Phase 3：语义验收

逐项执行 `checklists/semantic-acceptance.md`，重点判断：

- 路由是否明确；
- 问题澄清是否只针对真实决策；
- 输出粒度是否能够指导执行；
- Guardrails 是否保护真实风险；
- 示例是否值得模仿；
- 失败与阻塞是否有清晰处理；
- 文字是否简洁、明确、无互相矛盾。

## Phase 4：真实场景验证

至少覆盖：

1. 用户显式调用时进入；
2. 普通相似请求不会自动进入；
3. 新建通用 Skill；
4. 新建项目级定制 Skill；
5. 升级已有低质量 Skill；
6. 已知信息不会被重复询问；
7. 可从环境查明的信息不会转问用户；
8. 存在真实决策时每轮只问一个主要问题；
9. 用户确认设计前不会写文件；
10. 用户确认后只实施约定范围；
11. 能识别更适合放入 Hooks 或 CLI 的能力；
12. 能区分机械检查、语义验收和真实运行；
13. 失败后能够修复并重跑相关检查；
14. 交付报告能区分已验证、未验证和阻塞。

使用临时目录、夹具或隔离分支，避免验证污染真实项目。

## Phase 5：跨平台验证

分别记录：

- 平台的安装位置和显式调用方式；
- 是否关闭隐式调用；
- 平台专属配置是否隔离；
- 核心工作流是否保持单一规范源；
- 是否执行了真实运行测试；
- 未能运行时，完成了哪些静态检查。

## Phase 6：失败闭环

每个失败项记录：

```text
失败项：
复现命令或场景：
原因：
修复：
重跑范围：
最终结果：
```

只有修复后重新执行受影响检查并通过，才可标记为已验证。
