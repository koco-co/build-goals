# 需求包验证与交付

## Phase 1：机械校验

定位当前加载的 `build-prd` Skill 目录，执行 `python3 <build-prd-skill-dir>/scripts/validate_prd.py <current-project> --strict`；失败时修复并重跑至退出码 0。校验器负责目录、清单、哈希、编号互引、样例和来源等机械约束。

## Phase 2：语义验收

完整执行 `checklists/semantic-acceptance.md`，重点确认：

- 需求包能让不了解旧项目的实现者理解用户输入和正确输出；
- 正常行为样例完整；需求中确有追问、拒绝、恢复或边界行为时，相应样例能够区分结果；
- 已确认的固定结构与运行时可变信息没有混写；
- 公开契约已保留，内部实现没有污染新项目设计；
- 完整包无遗漏，阶段包边界闭合且外部依赖契约明确；
- 静态证据没有被描述为真实产品流程已运行。

语义检查失败时修订正式包，再重跑机械校验。

## Phase 3：写入范围检查

如果目标项目使用 Git，检查差异。本次调用只允许新增或修改：

```text
.build-goals/build-prd/
docs/产品需求/
```

迁移旧单文件 PRD 时，可以删除已经完成迁移的 `docs/PRD需求文档.md`。用户调用前已有的改动不归因于本 Skill，也不得覆盖。

## Phase 4：交付

最终回复包含：

- 需求包的可定位路径、包 ID、版本和完整包或阶段包类型；
- 功能域、功能、验收标准和行为样例数量；
- 实际覆盖的竞品、开源项目和官方规范数量；
- 实际执行的校验命令与结果；
- 实际运行过的产品流程，以及仅由静态证据确认的行为；
- 如果仍需下一上下文继续，使用 `§02-domain-confirmation.md` 中的交接提示词模板，按真实路径和当前功能域润色。

检查点不作为正式交付物推荐给 `vibe-coding`。只有通过严格校验的 `docs/产品需求/` 才能进入实施。
