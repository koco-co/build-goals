# 学习记录合同

本合同把一次学习单元定义为“可持久化、可验收、可恢复”的教学事务，避免知识只存在于聊天上下文。

## 1. 记录对象

- **知识点**：本单元中可以被单独解释、提问和验收的一个概念、边界或工作流判断。
- **覆盖**：知识点已经进入课程笔记，并有当前来源；覆盖不等于用户已经掌握。
- **验收**：用户回答了对应问题，模型完成评定，并把证据写回笔记。
- `knowledge_points_total`：本单元计划覆盖的知识点总数。
- `knowledge_points_covered`：已经完成用户验收的知识点数量。
- `knowledge_points_pending`：尚未完成用户验收的知识点数量。

`knowledge_points_covered + knowledge_points_pending` 应等于 `knowledge_points_total`。只讲过但用户尚未回答的知识点仍属于 `pending`。

## 2. 强制事务顺序

每次开始或继续一个单元都必须按以下顺序执行：

1. 用 Obsidian CLI 读取当前笔记和精确快照。
2. 建立或更新笔记中的“知识点清单”“覆盖矩阵”和“一道待回答题目”。
3. 通过 `roadmap_cli.py write-note` 先 dry-run，再 apply，并读回确认正文和 Properties 已落盘。
4. 只向用户发送当前知识块对应的一道题，发送后立即停止本轮，不继续讲新知识或发第二题。
5. 用户回答后，依据内部通过标准评定答案，把结论、依据/遗漏、下一步和题目状态写回同一篇笔记。
6. 再次通过 compare-and-swap 读回，更新掌握分、掌握证据、验收时间和知识点计数。

没有完成第 3 步时不得开始第 4 步；没有完成第 5～6 步时不得进入下一题或下一单元。

## 3. 笔记最低结构

正式学习或复习笔记必须按需包含：

- `knowledge_points_total`、`knowledge_points_covered`、`knowledge_points_pending`；
- `## 本单元知识点清单`：知识点 ID、标题、来源/正文位置、状态和对应题目；
- `## 学习目标与通过标准`：覆盖矩阵、边界和验收证据；
- `## 提问与验收` 或 `## One-shot 复习题`；
- `## 作答记录` 或等价的逐题记录；
- 来源、版本范围、`coverage_status` 和内容审计信息。

用户实际看到的学习题和复习题统一使用“进度状态行 → 场景 → 问题 → 提示”模板。进度状态行显示 `knowledge_points_covered/knowledge_points_total` 和当前题目状态；`提示`只说明回答方式，不展示内部通过标准或完整答案。

对于 `roadmap_kind: repository` 或 Vibe Coding 项目，题目默认停留在架构与用户流程层，优先考察职责、边界、输入输出、取舍和结果影响；内部状态名、API、文件路径、生成代码和实现步骤只有在用户主动要求源码或实现细节时才进入题目。

题目状态至少区分 `待回答`、`已通过`、`需补充`。没有用户答案的题目不能写成 `已通过`。

## 4. 状态与失败路径

- 当前笔记存在 `knowledge_points_pending > 0` 或题目状态为 `待回答` 时，恢复流程必须先继续当前题，不得选择新单元。
- 用户答案不足时保持 `learning_status: 学习中`，记录薄弱点并给出下一步；不得伪造掌握证据。
- 内容覆盖不足时保持 `coverage_status: 部分覆盖`，先补课程内容；不能用用户局部答对替代遗漏内容。
- 聊天中已经讲过但没有落盘的内容，回填时标记为 `已讲解/待回答`，不能直接标记为已掌握。
- 只有来源有效、`coverage_status: 完整`、所有必需知识点验收通过、正文已发布且掌握证据非空时，才能设置 `learning_status: 已掌握`。

## 5. 交付要求

每轮交付必须报告：课程笔记路径、知识点总数/已验收/待回答数量、当前题目状态、已写回的证据和唯一下一步。若正在等待用户回答，交付必须停止在该题，不得用“继续”代替答案。
