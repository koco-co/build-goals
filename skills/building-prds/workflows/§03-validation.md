# PRD 验证与交付

## Phase 1：机械校验

定位当前加载的 `building-prds` Skill 目录，执行其中的校验器：

```text
python3 <building-prds-skill-dir>/scripts/validate_prd.py <current-project>/docs/PRD需求文档.md --strict
```

校验器必须确认：

- 输出路径和主标题正确；
- 必需章节存在且顺序正确；
- 功能编号与验收编号存在、唯一且关联正确；
- 每项功能的输入、交互、文案、输出、边界、质量和验收结构完整；
- 竞品、开源项目和官方规范来源达到最低覆盖；
- 不含未决标记、模板占位或技术实现章节。

任何失败都必须修复后重新运行，直到退出码为 0。

## Phase 2：语义验收

完整执行 `checklists/semantic-acceptance.md`，重点确认：

- 所有产品角色、入口、功能、状态和跨功能旅程均已覆盖；
- 最终文案真实可用，输入输出示例能够直接理解；
- 外部最佳实践适用于当前产品且已经用户确认；
- 产品质量要求与验收标准只描述用户可观察结果；
- 没有把静态代码推断描述为真实运行证据。

语义检查失败时修订同一目标文件，再重跑机械校验和受影响清单。

## Phase 3：范围检查

如果目标项目使用 Git，检查工作区差异，确认本次调用只新增或修改：

```text
docs/PRD需求文档.md
```

用户在调用前已有的改动不归因于本 Skill，也不得覆盖。

## Phase 4：文档交付

最终回复包含：

- 目标文件的可定位路径；
- 实际覆盖的竞品、开源项目和官方规范数量；
- 实际执行的校验命令及结果；
- 已实际运行的产品流程范围。

如果没有真实运行某个用户可见流程，只能说明用于确认该行为的其他证据；不得把静态检查表述为真实交互已经通过。

完成条件：机械检查通过、语义清单通过、写入范围正确，用户能够直接审阅唯一的 PRD 文件。
