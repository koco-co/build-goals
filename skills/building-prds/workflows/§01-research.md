# 产品事实与最佳实践调研

## Phase 1：识别输入分支

先读取用户已经提供的上下文，不要求用户重新按模板填写。

- 已有项目：以当前工作目录为项目根，确认是否存在现有 `docs/PRD需求文档.md`。
- 产品想法：从用户的自然语言描述中提取产品作用、目标用户、核心场景、范围和限制。
- 已完成 `grill-me`：识别最终确认摘要、已确认决策和既有调研来源，不重复询问。

只有用户主动询问输入格式，或现有描述不足以识别产品主题时，才读取并展示 `templates/prd-intake.template.md`。

## Phase 2：分析已有项目

已有项目分支按产品事实需要读取：

- 项目规则、README、产品文档和已有 PRD；
- 产品界面、页面、路由、菜单、命令入口和用户可见配置；
- 覆盖产品行为的测试、示例、提示文案和帮助内容；
- 登录、引导、设置、权限、搜索筛选、导入导出、通知、后台管理和运营入口；
- Git 工作区状态，用于识别并保护用户已有改动。

代码只用于查明产品行为，不把内部模块、框架、数据结构或实现方式带入 PRD。

当项目可以在不产生外部副作用的前提下安全运行时，实际检查所有可访问的产品界面、入口和流程：

1. 记录角色、入口、主流程和跨功能旅程；
2. 检查加载、空状态、成功、失败、权限不足、取消和恢复状态；
3. 核对真实字段、校验规则、按钮和用户可见文案；
4. 不创建真实订单、发送消息、修改生产数据或执行其他外部副作用。

无法安全运行的产品行为必须通过现有证据或逐项用户确认形成确定结论，不能静默推断。

## Phase 3：梳理产品想法

产品想法分支至少需要形成以下完整轮廓：

- 产品解决的问题及作用；
- 目标用户、角色和使用场景；
- 用户进入、操作和离开的完整路径；
- 必须包含和明确排除的产品范围；
- 用户预输入与期望输出；
- 用户可感知的质量要求。

信息不足时，只在内部整理需要用户选择的决策，不提前起草 PRD。

## Phase 4：执行联网调研

每次生成或更新 PRD 都必须使用当前公开信息，最低覆盖：

- 2 个直接或相邻竞品的公开产品流程；
- 2 个仍活跃的相关开源项目；
- 适用的官方产品、交互、无障碍或行业规范。

调研要求：

1. 优先官网、官方帮助、官方演示、官方文档和源码仓库等一手来源；
2. 核对访问日期、发布日期、最近维护时间和适用版本；
3. 对比入口、信息结构、输入校验、交互反馈、异常恢复和无障碍做法；
4. 提炼适用于当前产品的候选方案，不复制受版权保护的文案或实现；
5. 每个来源记录名称、URL、访问日期和具体借鉴点；
6. 某类来源客观不存在时，向用户提交一个替代来源决策并等待确认，不得自行降低覆盖标准。

外部最佳实践不能直接成为产品需求。任何会改变产品范围、交互或验收结果的候选方案，都必须先转化为一个附带推荐答案的决策问题。

## Phase 5：建立产品矩阵

按以下类别整理内部工作矩阵：

```text
已验证的项目事实
用户已确认的产品决策
外部来源支持的推荐方案
仍需用户选择的决策
已覆盖的角色、入口、功能和状态
```

不得把工作矩阵写成 PRD 中的假设、开放问题或阻塞项。

完成条件：可自行查明的事实已经查明，强制来源覆盖达标，所有剩余内容都是需要用户明确选择的真实产品决策。
