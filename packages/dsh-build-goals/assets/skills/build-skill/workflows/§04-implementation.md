# 实施

本阶段只在用户确认的设计范围内创建或更新 Skill。

## Phase 1：冻结实施清单

在修改前记录：

- 允许新增、修改、移动和删除的路径；
- 必须保持兼容的接口；
- 预期验证命令；
- 不属于本次范围的内容；
- 需要另行授权的提交、推送、发布或破坏性操作。

发现设计依据已变化时，停止实施并回到设计阶段，不自行扩大范围。

## Phase 2：建立核心骨架

1. 先创建或更新 `SKILL.md`。
2. 默认使用推荐骨架（见 `templates/skill.template.md`），按 `rules/architecture.md` 的省略准则保留或省略各键；不为凑齐六键堆砌空章节。
3. 根据已确认的字段决策矩阵编写 Frontmatter；没有依据的可选字段保持省略。
4. Description 同时说明“做什么”和“何时使用”，并清楚描述独立分支；双平台 Skill 不依赖 Claude Code 专属字段承担唯一触发语义。
5. 将复杂细节移入按需读取文件，但保留完整入口和完成条件。

## Phase 3：按职责补充资源

按以下顺序实现：

1. 复用已有 CLI、测试和脚本；
2. 多个 Skills 确实共用相同稳定契约，且共享目录会随目标交付时，在项目根目录 `.agents/scripts/` 补充缺失的确定性脚本；否则补充 Skill 自有脚本；
3. 创建固定结构模板；
4. 创建可直接模仿的高质量示例；
5. 编写仍无法机械保证的规则；
6. 拆分复杂工作流；
7. 增加内容、文案或场景审查清单；
8. 只有存在多 Agent 编排时才增加 Prompt 模板。

每完成一个资源，立即确保：

- 有明确读取或执行入口；
- 路径真实存在；
- 与其他文件没有重复规范源；
- 不包含秘密、机器私有绝对路径或无意义占位内容。

新增脚本优先使用无需第三方依赖即可运行的 MJS 或 Shell。任务不适合时可以选择 Python 等语言；如果引入第三方依赖，同时落盘或引用目标项目采用的依赖声明，并实际运行已确认的安装与验证命令。

## Phase 4：完成内容初审

使用 `checklists/content-review.md` 检查正确性和完整性。内容存在歧义、缺失决策或权限不明时，先修复行为设计，不进入文案润色。

## Phase 5：文案审查

内容初审通过后使用 `checklists/copy-review.md`。需要改写参考时读取 `examples/copy-review.example.md`。

- 优化自然度、清晰度、简洁度和术语一致性；
- 删除重复规范与无作用句子；
- 不改变触发、流程、范围、权限、失败处理和完成条件；
- 无法确定原意时退回内容审查，不自行猜测。

文案修改后重新执行内容回归，并重跑受影响的静态检查或测试。

## Phase 6：项目级接入

项目级 Skill 必须优先遵循目标项目：

- 复用现有 CLI 和测试入口；
- 使用项目已有配置与目录；
- 不在 Skill 内复制业务实现；
- 两个及以上 Skills 已有真实共用需求时，可以把稳定脚本放在项目根目录 `.agents/scripts/`；必须确认该目录随项目交付，并让各 Skill 通过项目根目录命令调用同一规范源；
- 独立安装或发布不能携带 `.agents/scripts/` 时，脚本保留在对应 Skill 的 `scripts/`；
- Hooks 放在项目规定的位置；
- Skill 只描述模型需要的路由、判断和编排；
- 对稳定接口的变化提供迁移或兼容方案。

## Phase 7：平台适配

- 核心正文保持一致；
- 平台专属 Frontmatter、UI 元数据、策略或安装路径集中管理；
- 适配过程必须可重复、可测试；
- 不手工维护内容相同但容易漂移的两份 Skill；
- 平台不支持的能力要降级或明确标记，不伪造等价行为。

## Phase 8：实施自检

进入正式验证前确认：

- 所有已确认目标均有对应文件或行为；
- 所有新文件都有实际用途；
- 没有空目录、空文件、失效引用和重复规则；
- Frontmatter 与已确认矩阵一致，Codex 副本不会保留 Claude Code 专属字段；
- 内容审查和文案审查已完成，文案修改后的内容回归无新增问题；
- 变更没有越过用户确认范围；
- 未经授权的提交、推送或发布尚未发生。
