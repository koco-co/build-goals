# 工程选型规则

## 选择依据

每项工具、目录、配置和质量门禁必须对应至少一种事实：需求明确要求、目标运行环境要求、项目已有约定、所选生态的官方契约，或能够复现的现有问题。没有依据时不添加。

选型时比较当前官方支持、项目运行环境、团队约束、维护成本和实际收益。版本更新、社区流行度或“现代化”本身不是采用理由。

## 最小工程能力

项目只需具备：

- 一个真实运行入口；
- 可重复执行的安装或构建方式；
- 能验证已确认需求的命令。

只有项目实际需要依赖锁定、格式化、Lint、类型检查、pre-commit、CI、环境变量、结构化日志、秘密检查或多环境配置时，才选择对应工具并写入架构方案。

## 生态调研

从目标语言和框架的官方文档开始，核对其当前支持版本和原生工具。只有官方能力不满足已确认需求时，才比较第三方方案；职责重叠的工具不重复引入。

目录、命名、注释和公共接口遵循最终选定生态的真实规范。文件大小、函数复杂度和模块边界按可读性与职责判断，不设置没有项目依据的机械阈值。
