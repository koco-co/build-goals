# 基线建立与路线选择

## Phase 1: 保护当前工作

1. 记录：
   - 当前仓库绝对路径；
   - 当前分支与 HEAD SHA；
   - `git status --short`；
   - `git worktree list`；
   - 最近提交；
   - 已存在但未提交的文件和修改。
2. 将所有现有改动视为用户工作。只读取，不执行 reset、clean、stash、强制 checkout、历史改写或自动格式化全仓。
3. 如果目标目录不是 Git 仓库，记录这一事实；不要为了满足流程而擅自初始化 Git，除非任务方案明确包含初始化。
4. 如果发现并发 Agent、其他 worktree 或当前会话之外的提交，建立所有权表，避免重叠修改。

将 readiness 前已经存在的每个非当前 worktree 以“绝对或相对路径 | 完整分支引用 | 既有用途”写入基线；不存在时明确记录 `N/A（无既有 worktree）`。后续 readiness 只豁免这份冻结清单，任务中的 `Worktree` 写成 N/A、漏填路径或只写 TASK/分支名都不能豁免新建 worktree。

## Phase 2: 读取项目规则

按优先级读取：

1. 用户在当前会话给出的明确要求；
2. 仓库根目录及目标子目录中的 `AGENTS.md`、`CLAUDE.md`；
3. README、CONTRIBUTING、docs、ADR、开发规范；
4. 包管理、构建、测试、Lint、类型检查和 CI 配置；
5. 安全、环境变量、数据库和部署说明。

记录规则来源和适用范围。规则冲突时不自行选择会改变结果的一方；在架构方案中说明推荐处理。

同时把项目指令归类为：

- **有效沿用**：根文件、必要的局部文件和 `CLAUDE.md` 单一来源入口结构有效，内容与当前可验证事实一致；
- **需要更新**：文件存在，但链接、命令、目录、职责、安全边界或局部作用域已有明确缺口；
- **缺失**：没有根 `AGENTS.md`，或没有可用的 `CLAUDE.md` 单一来源入口。

这里只记录初步状态和证据，不修改文件。新建项目必须等脚手架命令实际建立后再确定正文；已有项目也要在基础工程变更稳定后复查，避免按即将被替换的事实生成指令。

## Phase 3: 选择执行路线

### PRD 驱动路线

满足以下条件时进入：

- `docs/PRD需求文档.md` 存在；
- 文档状态已经确认；
- PRD 可以通过 `scripts/validate_prd.py` 严格校验；
- 用户目标是实现 PRD 中的产品。

提取全部 `F-NNN` 和 `F-NNN-AC-NN`，建立需求追踪基线。

PRD 缺失、未确认或校验失败时，转交 `build-prd`。不得用代码现状或用户零散描述替代权威 PRD。

### 已有项目迁移路线

满足以下任一条件时进入：

- 用户要求架构审查、最佳实践升级或现代化迁移；
- 项目能运行，但目录、依赖、测试、配置或开发体验明显低质量；
- 用户要求基于竞品、官方资料和开源项目提出目标架构。

迁移路线不要求先存在 PRD，但必须区分产品行为保持项、允许调整项和纯工程治理项。

## Phase 4: 形成基线摘要

摘要至少包含：

- 执行路线与原因；
- 当前 HEAD 和工作区状态；
- 用户现有改动及保护方式；
- 技术栈、入口、运行方式、测试和 CI；
- 输入文档及其验证状态；
- 项目指令的初步分类、证据与待复查点；
- `rules/companion-skills.md` 中每项配套 Skill 的触发状态；
- 可用 Agent、worktree、浏览器和测试能力；
- 已知限制与阻塞；
- 下一阶段只读调研范围。

完成前不得修改项目。
