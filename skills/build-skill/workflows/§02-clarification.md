# 关键决策澄清

本阶段只处理无法自行查明，并且会改变 Skill 结构、行为或验收结果的决策。

## Phase 1：建立决策矩阵

把信息分为三类：

| 类别                     | 处理方式             |
| ------------------------ | -------------------- |
| 已由用户明确             | 直接采用，不重复询问 |
| 可从代码、文档或环境查明 | 自行调查，不询问用户 |
| 无法查明且会改变结果     | 纳入待确认决策       |

至少检查：

- 最终解决的问题与非目标；
- 通用 Skill 或项目级定制 Skill；
- 新建或兼容升级；
- 显式与隐式触发策略；
- 仅由用户调用、仅由模型调用，或两者都可调用；
- 是否需要调用参数提示或命名参数；
- 是否需要路径触发、独立上下文、指定 Agent、前台等待、固定模型或推理强度；
- 是否需要工具预授权、工具禁用、Skill Hooks 或指定内联命令 Shell；
- 是否存在必须写入 `compatibility` 的硬性环境要求；
- 各独立输入分支；
- 每个分支的输出、格式、命名和存放位置；
- 自动执行与必须确认的边界；
- 允许的副作用；
- 机械检查、真实验收和完成标准；
- Claude Code、Codex 或其他平台的支持范围；
- 是否允许修改稳定接口、目录或现有行为。

## Phase 2：筛选真正的问题

一个问题只有同时满足以下条件才允许提出：

1. 当前环境无法给出可靠答案；
2. 用户此前没有说明；
3. 至少两个合理答案会导致不同实现或验收结果。

不要询问偏好影响很小、可以采用安全默认值，或不会改变交付结果的问题。

## Phase 3：逐个提问

每轮只提出一个主要问题，格式如下：

```markdown
### 问题 N：<需要用户决定的事项>

**推荐：** <推荐答案>

**为什么会影响设计：**
<说明该决策会改变哪些目录、行为、产物或验收方式。>

**推荐理由：**
<结合已查明事实说明。>

**其他选择的影响：**

- 选择 A：...
- 选择 B：...
```

用户回答后：

1. 更新决策矩阵；
2. 检查回答是否解决了后续相关问题；
3. 不再重复询问已经覆盖的内容；
4. 继续下一个仍会改变结果的问题。

## Phase 4：结束澄清

不存在待确认决策时，输出简短结论：

```text
关键决策已明确，可以进入设计阶段。
```

如果从一开始就不存在待确认决策，明确记录：

```text
无待确认决策；全部关键条件均可由现有输入和环境确定。
```

不得为了表现流程完整而制造问题。

结束前按照 `rules/frontmatter.md` 形成初步字段决策矩阵。能够由平台契约、仓库约定或已确认行为确定的字段直接记录，不逐项询问用户；只有会改变调用、权限或执行方式的未知选择才进入提问。
