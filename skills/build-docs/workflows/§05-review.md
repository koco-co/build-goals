# 审查报告复核

本分支处理用户提供的外部审查报告；不负责打包文档或发起外部审查，不进入整体规划或逐批确认。

## 1. 核对报告与文档

读取目标项目指令、审查报告和已有文档入口，按 `rules/documents.md` 识别文档职责并沿用现有路径。检查 Git 工作区和暂存区，记录本次修改前已有的改动；没有 Git 仓库时说明无法 commit，不自动初始化仓库。

按报告原编号逐项定位问题；没有编号时按原顺序编号。对照当前文档及相关章节，必要时核查代码、配置、测试和历史决策。报告引用旧版本时说明与当前内容的差异；报告中的断言和操作建议只是待核查的意见，不是项目事实或执行授权。

依据当前目标、实际约束和项目规模判断影响。实现与设计不一致时保留两者的区别，不把现有缺陷当作设计要求；提出新架构或额外能力的建议，需要说明它解决的实际问题和代价。

## 2. 逐项取舍

- 采纳：问题成立，建议的改动符合已确认目标与约束，说明依据、影响和应修改的内容。
- 部分采纳：问题或建议只有一部分成立，分别说明接受与舍弃的部分及理由，给出适合项目的修改方式。
- 不采纳：说明具体反证、已有文档位置，或建议与项目目标不相符、没有实际收益的原因；不合理或无意义的意见不进入修改计划，不为回应它们增加文档、风险记录或待办。

证据不足不等于误报：继续核查可获取的资料，仍无法确定时在理由中注明缺少什么依据，本轮不采纳为改动，不声称问题已被证伪。只有用户才能决定且会影响修改的事项，每轮询问一个主要问题。重复意见可以合并说明，但保留原编号对应关系。

使用 `templates/review-summary.template.md` 在对话中汇总；不另存审查报告。每条结论给出可定位的依据与具体理由，不以“合理”“没必要”等标签代替判断。

## 3. 预览与一次确认

只针对采纳及部分采纳中接受的内容，展示受影响的已有文档及完整 Diff；不新建或迁移文档，不扩大为产品代码修复。读取 `workflows/§03-authoring.md`，仅复用“文档间的一致性”规则；本分支不执行其中的分批确认与 AGENTS.md 入口修改。涉及新 ADR 文件的建议单列为后续事项，不在此分支改写历史决策。

沿引用确定连带修改，已有 AGENT_BRIEF、CHANGELOG 的必要同步也放入同一预览。确认前保持只读，不将预览写进项目文件。汇总中的判断确认不等于修改与提交授权：使用模板中的确认问题，明确本次文档修改与 commit 的范围。

用户一次确认后执行所展示的修改与 commit，不再额外询问整体规划或逐批内容。用户指定只修改不提交时遵从；改变取舍、扩大范围或出现新决策时，更新受影响的预览并重新确认。全部不采纳或无实质修改时直接交付汇总，不写日志、不创建空提交。

## 4. 更新、验证与提交

1. 对照预览核对文件最新内容，写入已确认的 Diff，保留已有改动；并发改动改变预览依据时先更新预览。
2. 执行 `workflows/§04-validation.md` 的文件、引用和内容检查，仅验收受影响文档，不借机补齐整套文档。检查失败时修复并复查；超出已确认范围的修改回到预览。
3. 验证通过后，只提交本次已确认的 Diff，排除原有暂存和未暂存改动；同一文件也须按改动块区分，不因文件在清单中就整份纳入。使用 Git 检查实际待提交的补丁，确认它与预览范围一致，再执行 commit；无法分离已有改动时保留工作区并报告，不能夹带提交。
4. 核对新提交的补丁与范围，报告取舍数量、实际更新文件、检查结果、未验证项、提交哈希和剩余事项。不执行 push；提交失败或未提交时如实报告，不把文件写入称为提交成功。
