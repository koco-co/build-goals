# 逐功能域确认与过程检查点

## 1. 逐域处理

按照已确认依赖顺序，每次只处理一个功能域。加载内容仅限：

- 已确认的功能域地图；
- 当前功能域的产品事实、公开契约和调研证据；
- 当前功能域直接依赖的已确认结论；
- 影响全局输入输出或跨域旅程的已确认规则。

不要为了“了解背景”重新加载整个旧项目或所有已完成域。需要补查旧项目时，只读检查当前问题所需的最小范围。

## 2. 决策顺序

每次只询问一个会改变最终产品结果的问题，并给出推荐答案和依据。按以下顺序推进：

1. 域范围、角色、入口与前置条件；
2. 每项功能的作用和用户旅程；
3. 用户会提供的输入、缺失信息和需要追问的内容；
4. 正常、不完整、无效、不适用和边界输入；
5. 产品行为、状态、最终提示文案和恢复路径；
6. 输出内容、固定结构、语义要求和运行时可变信息；
7. 命令、路径、字段、格式、公开 API 或文件等对外契约；
8. 禁止结果、产品质量要求和验收标准。

不按问题数量保存，不以“每十题”为界。一个功能域无论问多少题，都必须在域内结论闭合后再保存。

## 3. 功能域确认

域内所有决策完成后，在对话中给出一份可审阅总结，至少包含：

- 功能与稳定编号；
- 代表性用户输入和行为样例；
- 交互、追问、状态与最终文案；
- 输出契约三部分：固定结构、语义要求、运行时可变内容；
- 必须保持的外部契约与明确允许重新设计的内部内容；
- 异常、边界、禁止结果和验收标准；
- 直接依赖及其已确认契约。

只有用户明确确认整个功能域总结后，才写过程检查点。不要对总结中的每一小节重复确认。

## 4. 写入过程检查点

检查点固定写入：

```text
.build-goals/build-prd/
├── 会话.yaml
└── 功能域/
    └── <功能域-id>.yaml
```

- 使用 `templates/checkpoint-session.template.yaml` 和 `templates/checkpoint-domain.template.yaml`。
- `.yaml` 内容使用 YAML 1.2 可直接读取的 JSON 对象形式，避免依赖额外解析库。
- `会话.yaml` 记录来源、已确认功能域地图、当前域、已完成域、待处理域和直接依赖。
- 功能域检查点只记录用户已确认的最终结论、代表性行为样例和证据引用，不记录访谈逐字稿、工具调用、模型思考或失败尝试。
- 写入后执行 `python3 <build-prd-skill-dir>/scripts/validate_checkpoint.py <current-project> --strict`；通过后自动进入下一个待处理域，不再询问是否继续。

检查点的 `status` 只能是 `confirmed`。未确认的草稿只保留在当前对话，不写文件。

## 5. 跨上下文续接

上下文即将结束或用户要求交接时，最终回复必须给出可直接复制的提示词，例如：

```text
继续使用 build-prd 完成 <项目绝对路径> 的产品需求包。先读取 <项目绝对路径>/.build-goals/build-prd/会话.yaml 和其中列出的已确认功能域检查点；保持已确认结论不变，从 current_domain 指向的功能域继续，一次只询问一个会改变产品结果的问题。所有功能域完成并通过跨域确认前，不要生成 docs/产品需求/ 正式需求包。
```

根据真实路径、当前功能域和阻塞原因润色提示词，不输出抽象占位符。

## 6. 结束逐域阶段

全部功能域确认后，执行一次跨域审查：

- 跨域用户旅程是否连续；
- 共享输入输出、身份、权限、文案和状态是否一致；
- 直接依赖是否都有明确契约；
- 同一公开命令、路径、格式或 API 是否出现冲突；
- 是否存在功能遗漏、重复或不可验收结果。

只询问审查中新出现的决策。用户确认跨域总结后，进入正式需求包编写；未变化的域不重复确认。
