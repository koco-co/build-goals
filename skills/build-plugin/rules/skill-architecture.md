# Skill 架构规则

## 1. 最小充分结构

每个 Skill 必须包含 `SKILL.md`。其他目录只在存在独立职责时创建：

| 目录          | 职责                               | 创建条件                            |
| ------------- | ---------------------------------- | ----------------------------------- |
| `workflows/`  | 完整工作流、独立分支或较长阶段     | 主流程无法在 `SKILL.md` 中保持清晰时 |
| `templates/`  | 输出产物的空白结构                 | 产物字段或布局固定时                |
| `examples/`   | 模型可以直接模仿的完整示例         | 输出粒度、风格或边界需要示范时      |
| `rules/`      | 必须遵守但不能完全由脚本保证的规范 | 存在跨工作流共享约束时              |
| `scripts/`    | 单个 Skill 自有的格式化、转换和机械校验 | 存在确定性处理、仓库无可复用实现，且不满足共享脚本条件时 |
| `checklists/` | 内容、文案、场景或人工审查         | 无法可靠地用代码完成检查时                  |
| `prompts/`    | Subagent 的角色与返回协议          | 确实存在多 Agent 编排时             |
| `references/` | 简单 Skill 的辅助资料              | 内容不值得拆为专用目录时            |
| `assets/`     | 输出中复制或嵌入的静态资源         | 产物需要图片、样式或二进制资源时    |
| `agents/`     | 平台展示或策略元数据               | 目标平台明确支持且需要时            |

不要创建空目录或“以后可能有用”的占位文件。

## 2. `SKILL.md` 职责与推荐章节结构

只负责入口和主流程：目标、路由、步骤、交付与必须遵守的边界；详细规则、长示例、模板正文和复杂分支移入附属文件。`SKILL.md` 应便于快速浏览，并尽量不超过 500 行。

以下章节结构**仅供参考，并非必须采用**：

| 键               | 意图                         | 可省略的情形                       |
| ---------------- | ---------------------------- | ---------------------------------- |
| `# Outcome`      | 一句话说明最终结果           | 不建议省略                         |
| `## Routing`     | 什么输入进入哪个分支、何时退出或转交 | 没有独立分支时可并入 Steps   |
| `## Steps`       | 主流程步骤                   | 不建议省略                         |
| `## Delivery`    | 交付物与汇报要求             | 输出已在别处说明时可并入           |
| `## Guardrails`  | 数据、权限、副作用红线       | 没有此类红线时省略                 |
| `## References`  | 按需读取的附属文件索引       | 没有附属文件时删除整节，不要留「无附加文件」空节 |

## 3. 工作流拆分

工作流文件采用：

```text
§01-name.md
§02-name.md
...
§NN-name.md
```

拆分依据是独立职责，不是字数。一个文件内容较长时，在文件内使用 `Phase 1` 至 `Phase N`，不要把连续段落机械切碎。

## 4. 模板与示例

- 模板命名：`<artifact>.template.<extension>`；
- 示例命名：`<artifact>.example.<extension>`；
- 模板规定空白结构和必填字段；
- 示例展示完成后的高质量结果；
- 同一内容不得同时作为模板和示例保存。

## 5. 脚本与清单

- 脚本处理可重复、可确定、可由退出码判断的检查；
- 清单处理内容完整性、业务合理性、表达质量和场景覆盖；
- 已由脚本保证的项目不要在清单中逐项重复；
- 脚本必须有明确输入、输出、错误信息和非零失败退出码。

### 5.1 多 Skill 共享脚本

同时满足以下条件时，多个项目级 Skills 可以共用项目根目录 `.agents/scripts/<script>`：

- 至少两个 Skills 已有真实调用需求，不为未来可能复用而提前抽取；
- 脚本职责稳定，调用方使用相同输入、输出和失败契约；
- `.agents/scripts/` 会随项目或整体安装包一起交付，并能在目标环境中解析；
- 共享脚本是唯一规范源，各 Skill 只记录项目根目录调用命令，不保存内容副本。

只被一个 Skill 使用，或独立安装、复制、发布时无法保证共享目录存在的脚本，保留在该 Skill 的 `scripts/`。设计方案必须写明共享脚本的调用方、交付方式、运行环境和验收命令。

新增脚本优先使用无需第三方依赖即可运行的 MJS 或 Shell，根据结构化数据处理、跨平台需求和命令编排复杂度选择。XLSX 等任务不适合 MJS 或 Shell 时，可以采用 Python 等更合适的语言；需要第三方包时，同时声明依赖、安装方式和可复现运行命令。

## 6. Prompt 与 References

- 不涉及 Subagent 时不创建 `prompts/`；
- 简单 Skill 可以只用 `references/`；
- 复杂 Skill 应将内容移入职责更明确的目录；
- `references/` 不能成为无法分类内容的堆放区。

## 7. Skill 外部能力

以下能力通常应放在 Hooks、CI、CLI 或项目公共模块中：

- 每次事件都必须自动执行的操作；
- 权限拦截；
- 环境初始化；
- 与模型推理无关的固定转换；
- 多个 Skills 共用的稳定业务实现；
- 已由目标项目提供的校验或生成器。

设计方案必须明确这些能力的位置、触发时机、输入输出和授权边界。
