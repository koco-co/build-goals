# 调研与工作流选择

## 共同入口

确认目标项目与本次文档范围，读取适用的项目指令并查看工作区状态。先检查已有文档及其入口，再读取与需求有关的代码、配置、测试、构建命令和 Git 记录；按模块追踪证据，不无差别读取整个仓库。

以跨模块协作、阶段依赖和多会话接续的实际需要判断是否属于大型项目，不按代码行数设门槛。局部修复或小需求不进入整套文档流程。

## 从零建立

提取目标用户、功能范围、业务实体、阶段及验收要求。只追问无法查明且会改变文档的决策，每轮一个主要问题并给出建议。用户已确认的内容直接沿用。

尚无实现的架构、字段和命令属于设计，不写成已实现或已验证；技术选型和关键行为得到确认后才作为开发约束。

## 已有项目提取

按以下来源建立当前事实，而不是要求用户重新口述整个项目：

| 来源 | 提取内容 | 证据边界 |
| --- | --- | --- |
| 代码入口、模块、调用链 | 已实现功能、层次、依赖和实际状态变化 | 代码存在不等于功能通过验收 |
| Schema、类型、迁移、持久化代码 | 实体字段、关系、ID 和存储约束 | 以有效实现为现状依据，冲突单列 |
| 配置、依赖声明、脚本、CI | 技术栈、规范与运行命令 | 命令已定义不等于已成功运行 |
| 测试及已有运行结果 | 已覆盖场景与已验证行为 | 分别说明测试是否存在、是否通过，以及真实端到端验证的执行情况与结果 |
| 已有文档、ADR、Git 记录 | 明确的目标、历史变更和已记录决策 | 只采用可追溯的日期和历史理由 |

将结论区分为现状事实、已确认目标和待确认项，附相关文件或记录定位。现状与目标不一致时展示差异，不直接改代码，也不把当前缺陷转成设计要求。

例如：配置定义了测试命令，可以写入“已定义”；只有实际运行结果才能写“已验证”。代码采用了某种存储格式，可以记录现状；没有决策记录时，不编造选择它的理由或被否决的备选方案。需要建立 ADR 时记录本次确认日期，并注明历史理由未知。

## 持续更新

先读现有 AGENT_BRIEF、ROADMAP 与 CHANGELOG，定位本次需求、相关 Diff、测试结果及新决策。历史缺失时只补可证实的现状，不凭猜测补写过去的会话记录。

沿文档引用和模块依赖确定受影响范围；已有且未受影响的文档保留。已完成任务是否可勾选，取决于任务自己的 Definition of Done 和证据，不只看代码提交。

## 输出

在对话中简短列出工作流、证据来源、现有文档缺口和待确认决策，交给整体规划；此阶段不写项目文件。
