# TDD 与质量门禁

## 1. 按任务类型选择首个验证证据

行为代码、缺陷修复和可自动验证的契约变更优先遵循 Red-Green-Refactor：

1. **Red**
   - 写最小失败测试；
   - 运行并确认失败原因确实是目标能力缺失；
   - 不接受语法错误、环境损坏或错误 fixture 造成的假红。
2. **Green**
   - 实现让目标测试通过的最小行为；
   - 不提前实现未确认范围。
3. **Refactor**
   - 改善命名、模块边界、重复、错误处理和类型；
   - 保持所有测试通过。

不是所有任务都适合人为制造“失败测试”。实施任务必须先声明任务类型，并在修改前定义可复核的首个验证证据：

- 行为代码、Bug、API/数据契约：失败测试或能稳定复现旧行为的测试；
- 文档：现有文档缺口、链接/命令校验失败或明确的内容验收检查；
- 配置、CI、构建：配置解析、dry-run、lint、workflow 校验或修改前可观察的失败命令；
- 数据/架构迁移：现状行为测试、迁移前后契约对比、dry-run 或可回滚迁移检查；
- 生成文件：生成器输入、确定性输出 diff 和生成后校验。

无法自动化的验收仍需要先定义可观察步骤和证据。不得为了满足格式要求创建没有产品价值的假测试。

## 2. 测试层次

按项目适用性覆盖：

- 单元测试：纯逻辑、边界和错误；
- 组件测试：UI/组件状态和交互；
- 集成测试：数据库、文件、队列、外部适配层；
- 契约测试：API、事件和插件接口；
- E2E：关键用户旅程；
- 视觉回归：有界面的稳定关键视图；
- 性能与恢复：需求包或架构明确要求时。

E2E 不替代单元与集成，覆盖率数字不替代有效断言。

## 3. 测试数据

正常数据必须：

- 与业务字段和关系一致；
- 可重复创建；
- 不依赖生产；
- 不包含真实个人信息或秘密；
- 能覆盖主路径、权限和至少一个边界；
- 有清理或隔离策略；
- 前端、API 和数据库可共同观察。

优先使用 factory、fixture、seed 或测试容器，不提交手工临时数据库。

## 4. 门禁顺序

推荐从快到慢：

1. 格式；
2. Lint；
3. 类型；
4. 目标单元测试；
5. 目标集成测试；
6. 构建；
7. 全量单元与集成；
8. E2E；
9. 视觉、无障碍和安全；
10. 打包或部署等价检查。

本地命令与 CI 使用同一入口。

## 5. 失败处理

- 先定位首个可信根因；
- 修复实现或测试数据，不降低验收；
- 受影响检查重跑后再运行全量门禁；
- flaky test 必须定位并修复，不靠无限重试；
- 外部环境阻塞时保留失败证据并标记未验证。

## 6. 不适用分支

没有 UI 时不创建视觉测试占位；没有数据库时不创建迁移测试；没有外部 API 时不创建虚假契约层。文档、配置和 CI 任务没有合理的 Red 测试时，记录其任务类型和替代验证证据，不机械补“第一条失败测试”。交付中说明为何不适用。

## 7. 结构化命令证据

对关键自动化验证，可使用 `scripts/run_evidence.py` 把执行上下文保存为结构化记录：

```text
python3 <vibe-coding>/scripts/run_evidence.py \
  --output <evidence.json> \
  --summary "<本次验证说明>" \
  -- <真实验证命令及参数>
```

记录包含 cwd、命令参数、开始/结束时间、退出码，以及 stdout/stderr 的字节数、行数和 SHA-256；默认不把完整日志复制进证据文件，降低意外持久化秘密的风险。证据文件在支持 POSIX 权限的平台上写为 `0600`。

这类记录只能说明包装器当时观察到的执行结果，后续仍可被编辑，因此**不是不可篡改的执行证明**。静态校验器不得仅凭该 JSON 宣称命令真实执行；仍需结合 CI、测试系统、真实客户端或人工验收等独立证据。普通低风险命令不要求机械生成证据文件。
