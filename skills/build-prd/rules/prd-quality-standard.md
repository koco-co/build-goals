# 产品需求包质量标准

## 1. 事实、决策与证据

每个结论必须来自至少一种可说明的依据：实际验证的产品行为、用户可见文档或测试、用户明确确认的目标决策、已确认采用的外部实践。

代码只能证明实现线索，不能自动证明产品意图。现状、文档和目标冲突时先让用户选择。正式包不使用“可能”“建议考虑”掩盖未决问题，也不保留 TODO、TBD、假设、开放问题或待确认项。

## 2. 正式内容与过程内容

正式需求包记录最终产品事实、已确认决策、必要设计依据和可复核样例。以下内容只属于过程检查点或当前对话，不进入正式包：

- 访谈逐字稿和问题顺序；
- 模型推理、工具调用、失败尝试和临时猜测；
- 旧项目内部架构、技术栈、模块、数据库、内部 API 与代码组织；
- 工程任务、部署步骤、排期、预算和组织分工。

过程检查点固定在 `.build-goals/build-prd/`，不得被当作可实施需求。

## 3. 目录与单一事实源

正式结构固定为：

```text
docs/产品需求/
├── PRD需求文档.md
├── 需求包清单.yaml
├── 功能域/<功能域>.md
└── 行为样例/{产品行为样例集.yaml,<功能域>.yaml}
```

旧的 `docs/PRD需求文档.md` 不得与新包长期并存。包内只能是普通文件；不得使用符号链接、绝对路径或 `..` 引用来源项目。清单声明全部文件并记录真实 SHA-256。

## 4. 功能域与编号

- 功能域按用户业务能力划分，使用稳定的小写连字符 ID；文件名使用用户可读名称。
- 每项功能使用唯一且稳定的 `F-NNN`；更新时沿用有效编号，废弃编号不重新分配。
- 验收标准使用 `F-NNN-AC-NN`，只能归属于对应功能。
- 行为样例 ID 在整个包内唯一，并由对应功能文档完整引用。
- 功能域依赖必须指向清单内功能域，或以正式外部依赖契约声明；不得形成依赖环。

完整包覆盖全部已确认产品能力。阶段包必须列出纳入域、延后域和独立验收边界，且每项外部依赖都有明确输入、输出与失败行为。

## 5. 用户输入契约

每项功能的输入表格至少包含：输入项、提供者、必填、格式与范围、默认值、校验规则、正确示例、错误示例。

输入不仅是表单字段，也包括用户的自然语言提示、命令参数、文件、目录、选择、已有状态和上下文。已有项目需要保留真实且有代表性的用户输入；涉及敏感数据时使用不改变行为含义的脱敏样例，并标记 `sensitive_data=sanitized`。

信息不足时必须写明产品会追问什么、一次追问几个问题、哪些内容可以推导、哪些内容必须由用户决定。

## 6. 交互、文案与恢复

每项功能写明用户入口、操作顺序、产品反馈和退出方式。状态文案表格至少覆盖适用的加载、空状态、成功、失败、权限不足、取消和恢复。

文案必须是可以直接显示给用户的最终文本。禁止使用“友好提示”“显示错误信息”“文案后定”等抽象描述。错误反馈说明发生了什么、保留了什么输入以及用户下一步能做什么。

## 7. 输出契约

每项输出必须分别说明：

- 固定结构：必须完全一致的文件路径、标题、字段名、字段顺序、枚举、命令格式或机器可读结构；
- 语义要求：表达可以变化，但必须覆盖的含义、事实、建议和用户下一步；
- 运行时可变内容：ID、时间、耗时、环境值、动态数量等允许变化的信息及其格式边界。

输出表格至少包含输出内容、呈现形式、触发条件、上述三类约束和完整示例。只有产品本身要求 JSON、YAML、Markdown、文件或提示词结构时，才附完整结构化示例。

## 8. 对外契约与实现自由

需求包必须记录用户或外部系统已经依赖的命令、路径、格式、公开 API、文件结构、错误码和兼容规则。默认要求保持这些外部可观察行为；新项目可以重新设计框架、模块、数据库和内部流程。

只有用户明确确认的目标变化可以改变外部行为。架构升级或技术栈迁移本身不是改变产品行为的理由。

## 9. 行为样例

每项功能至少包含：

- `normal`：典型完整输入与正确结果；
- `clarification`：信息不足时的追问与后续结果；
- `invalid` 或 `not_applicable`：拒绝、不适用或可恢复错误；
- `boundary`：长度、数量、状态、权限或格式边界。

每个样例必须记录用户输入、起始状态、期望行为、期望输出、输出三类约束、可检查断言、禁止结果和敏感数据状态。不得只写一句“正常工作”。

## 10. 产品质量与验收

只写用户可观察、可重复检查的结果，例如反馈时间、角色权限、隐私告知、焦点与键盘行为、兼容范围和失败恢复。不要规定缓存、数据库、服务、框架或部署方式。

每个主流程和适用分支都要有 Given/When/Then 验收标准：Given 是用户可建立状态，When 是用户操作或可观察事件，Then 是唯一、具体、可检查的外部结果。

## 11. 调研质量

最低覆盖为 2 个竞品、2 个活跃开源项目和 1 个适用官方规范。每条来源包含类型、名称、直接一手 URL、实际访问日期和具体借鉴点。调研只形成候选方案，用户确认后才能写成产品要求。

## 12. 清单与版本

- `schema_version` 描述需求包格式版本；当前为 `1.0`。
- `package_version` 使用 SemVer。兼容性补充递增 patch；新增兼容功能域或功能递增 minor；确认改变或移除外部行为时递增 major。
- `status` 只有全部纳入内容已确认时才可写 `confirmed`。
- `package_type` 只能是 `full` 或 `stage`。
- 清单来源用于追溯快照，不是运行时引用；复制后的包必须自包含。
