# 最终验收标准

## 选择原则

只执行有需求、架构方案、项目事实、可复现缺陷或明确安全边界支持的验收项。不得为填写报告而补设测试层、异常路径、权限、配置、UI、安全或兼容要求，也不得要求项目逐项证明“不适用”。

## 所有项目都要满足

- 需求包纳入范围内的功能、验收 ID 和行为样例有实现与验证证据；迁移路线中本次纳入的 Finding 有明确结果。
- 架构、任务、代码、验证和文档一致，未确认的新功能没有混入交付。
- 安装或构建方式和真实运行入口可重复执行。
- 本次任务采用的质量门禁通过，没有通过删除测试、弱化断言、排除文件或关闭规则掩盖失败。
- 每个功能单元有独立 commit 和回滚边界，最终工作区状态准确。
- 完成结论有命令、测试报告、提交、截图、交互记录或可重复人工步骤支持；文件存在本身不等于行为通过。

## 按项目事实增加

- 有持久化或复杂业务状态时，使用能复现对应验收的数据，并验证实际要求的角色、权限、关联或状态。
- 有 UI、GUI、TUI 或可视组件时，只验证需求明确的视口、状态、交互、文案、视觉和无障碍要求。
- 有多个入口或消费者共享契约时，验证输入、输出、状态、错误、命名和文档使用同一权威定义。
- 需求包含失败或恢复行为时，验证对应错误处理和恢复结果。
- 项目使用环境变量、认证、授权、日志、秘密或供应链检查时，验证已经声明的边界和真实结果。

所有未执行项按真实原因标为未验证，不扩张结论。
