# PRD 编写与现有文件合并

## Phase 1：写入条件

只有同时满足以下条件才开始编写：

- 强制联网调研达到最低覆盖；
- 所有产品事实已有证据或用户确认；
- 功能范围、角色、输入、输出、交互、文案、质量要求和验收结果均已确定；
- 没有假设、待定项、开放问题或阻塞项；
- 用户已经给出确认结论，或同一主题此前的 `clarify-goal` 确认结论与调研均已完整。

任一条件不满足时继续调研或逐项确认，不写入部分 PRD。

## Phase 2：处理文档

目标固定为当前目录的 `docs/PRD需求文档.md`。

文件已存在时：

1. 将其作为当前产品需求基线完整读取；
2. 保留仍有效且已经确认的产品要求及稳定功能编号；
3. 对冲突内容在写入前逐项确认；
4. 删除已经明确废弃、重复或被新决策取代的内容；
5. 最终重建为一份结构统一的权威文档，不追加第二套章节；
6. 不创建备份文件或第二份 PRD。

## Phase 3：组织内容

完整读取 `templates/prd.template.md` 和 `rules/prd-quality-standard.md`。需要确认完成粒度时读取 `examples/prd.example.md`。

已有项目必须把“已实现现状”和“目标需求”明确分开；产品想法则把已确认的起点事实和目标产品分别写入对应位置。

每项功能使用稳定的 `F-NNN` 编号，并完整填写：

- 作用与目标；
- 适用角色、入口与前置条件；
- 用户预输入表格及正反示例；
- 主流程和所有适用分支；
- 状态、触发条件、最终文案与后续动作；
- 期望输出表格及完整示例；
- 异常、边界与恢复；
- 用户可感知且可验收的产品质量要求；
- 设计依据；
- 与功能编号关联的 Given/When/Then 验收标准。

## Phase 4：产品边界

允许写入产品作用、用户、功能、交互、内容、文案、权限体验、隐私提示、无障碍、兼容范围、响应目标和用户可观察结果。

不得写入：

- 技术架构或系统架构；
- 技术栈、框架、库或选型；
- 数据库表、内部数据模型或存储方案；
- API、内部接口、服务拆分或通信协议；
- 部署、运维、工程任务或代码实现；
- 市场规模、商业计划、预算、排期或组织分工。

## Phase 5：文档落地

先在当前上下文中形成完整文档，再创建 `docs/`（如不存在）并一次性写入目标文件。不要边访谈边写入半成品。

写入后立即进入验证；校验失败时只修复同一目标文件并重新运行，不留下临时文档。

完成条件：目标路径包含一份内容完整、结构统一、全部决策已确认的产品 PRD，目标项目没有其他文件被修改。
