# vibe-coding 工作流状态与权限

本文件是 `vibe-coding` 阶段门禁的唯一权限表。`SKILL.md` 与各 workflow 只描述阶段动作，不得自行扩大这里定义的写入、Git 或确认权限；出现冲突时以本表为准并停止实施，先修正规则漂移。

| 状态 | 进入条件 | 允许读取 | 允许写入 | 允许 Git 操作 | 下一道门禁 |
| --- | --- | --- | --- | --- | --- |
| `baseline_readonly` | Skill 已路由，尚未获得第一次全局架构确认 | 用户授权范围内的项目事实、需求来源、旧项目参考范围、公开资料 | 无；外部需求包只允许校验和比较 | `status`、`log`、`diff`、`worktree list`、`rev-parse` 等只读命令 | 第一次全局架构确认 |
| `architecture_approved` | 用户确认完整架构方案 | 与架构、需求快照和规划直接相关的材料 | 路线 1–3 可把已校验需求包复制到 `docs/产品需求/`；路线 1–3 写 `docs/架构设计/`，路线 4 写 `docs/架构迁移/`；不得创建 `docs/实施任务/` | 仍只读；不得创建分支、worktree 或 commit | 第二次全局实施路线确认 |
| `plan_approved` | 用户确认整体实施路线、并行边界、提交策略和验收矩阵 | 已确认需求、架构、任务直接依赖及必要工程事实 | 写 `docs/实施任务/`；允许脚手架、治理文件和已确认任务范围内的项目修改 | 可创建已展示范围内的本地分支、worktree 和本地原子 commit；不含 push、受保护分支合并、发布或部署 | readiness 严格校验 |
| `implementing` | plan 阶段严格校验与 readiness 通过 | 当前任务、直接依赖契约和必要工程事实 | 已确认任务范围内的代码、测试、配置和本域交付证据 | 仅已确认范围内的本地任务分支、worktree、原子 commit 和满足清理条件的本轮任务 worktree/分支 | 全部任务完成并进入全链路验证 |
| `validated` | 本域、跨域和适用 E2E/质量门禁完成 | 交付核验需要的全部已确认产物和验证结果 | 更新任务状态、验证证据与 `docs/交付验收/` | 只允许为已确认任务补齐必要的本地交付 commit；不得 push、受保护分支合并、发布或部署 | 最终严格校验 |
| `delivered` | 最终严格校验完成并已报告未验证/阻塞项 | 交付报告与最终仓库事实 | 除用户新授权的修复外停止写入 | push、受保护分支合并、发布、部署、本地 Plugin 更新分别等待明确授权 | 用户授权的外部动作 |

## 通用规则

- 第一次架构确认不会授权本地 Git 写操作；第二次全局确认才授权已展示范围内的本地分支、worktree 和原子 commit。
- 路线 1–3 的外部需求包在 `baseline_readonly` 只校验、比较和展示差异。首次复制和已确认替换都只能在 `architecture_approved` 或更晚状态执行；已有不同快照的替换仍需单独说明影响并取得明确确认。
- 第二次确认前只在对话中展示完整实施路线。`docs/实施任务/` 必须在第二次确认后一次性写入，不能用“为了规划”作为提前落盘理由。
- 非 Git 项目不满足本 Skill 的 Git 前置条件。基线阶段只报告事实并询问是否初始化 Git；用户同意后才能初始化并重新建立基线，用户拒绝则停止本 Skill，不静默降级成无 Git 交付。
- 配套 Skill、子 Agent 和 workflow 都继承当前状态权限，不能因为子流程自身具备写能力而越过上层门禁。
- `implementing` 中自动清理只适用于本轮创建、已集成、检查通过、worktree 干净且无独有提交的任务 worktree/本地任务分支；既有 worktree、用户分支和不满足条件的对象不得清理。
- 任何需要回到前一道全局决策的问题，都先将状态退回对应门禁；不得在旧授权下继续扩大范围。
