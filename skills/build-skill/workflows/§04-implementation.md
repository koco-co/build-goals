# 实施

本阶段只在用户确认的设计范围内创建或更新 Skill。

## Phase 1：冻结实施清单

在修改前记录：

- 允许新增、修改、移动和删除的路径；
- 必须保持兼容的接口；
- 预期验证命令；
- 不属于本次范围的内容；
- 需要另行授权的提交、推送、发布或破坏性操作。

发现设计依据已变化时，停止实施并回到设计阶段，不自行扩大范围。

## Phase 2：建立核心骨架

1. 先创建或更新 `SKILL.md`。
2. 保留 `Outcome`、`Routing`、`Steps`、`Delivery`、`Guardrails` 和 `References` 的核心顺序。
3. Frontmatter 只写目标平台实际支持的字段。
4. Description 同时说明“做什么”和“何时使用”，并清楚描述独立分支。
5. 将复杂细节移入按需读取文件，但保留完整入口和完成条件。

## Phase 3：按职责补充资源

按以下顺序实现：

1. 复用已有 CLI、测试和脚本；
2. 补充缺失的确定性脚本；
3. 创建固定结构模板；
4. 创建高质量 Few-shot 示例；
5. 编写仍无法机械保证的规则；
6. 拆分复杂工作流；
7. 增加语义验收清单；
8. 只有存在多 Agent 编排时才增加 Prompt 模板。

每完成一个资源，立即确保：

- 有明确读取或执行入口；
- 路径真实存在；
- 与其他文件没有重复规范源；
- 不包含秘密、机器私有绝对路径或无意义占位内容。

## Phase 4：项目级接入

项目级 Skill 必须优先遵循目标项目：

- 复用现有 CLI 和测试入口；
- 使用项目已有配置与目录；
- 不在 Skill 内复制业务实现；
- Hooks 放在项目规定的位置；
- Skill 只描述模型需要的路由、判断和编排；
- 对稳定接口的变化提供迁移或兼容方案。

## Phase 5：平台适配

- 核心正文保持一致；
- 平台专属 Frontmatter、UI 元数据、策略或安装路径集中管理；
- 适配过程必须可重复、可测试；
- 不手工维护内容相同但容易漂移的两份 Skill；
- 平台不支持的能力要降级或明确标记，不伪造等价行为。

## Phase 6：实施自检

进入正式验证前确认：

- 所有已确认目标均有对应文件或行为；
- 所有新文件都有实际用途；
- 没有空目录、空文件、失效引用和重复规则；
- 变更没有越过用户确认范围；
- 未经授权的提交、推送或发布尚未发生。
