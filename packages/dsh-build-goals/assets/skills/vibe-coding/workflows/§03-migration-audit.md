# 现有项目架构或技术栈迁移

开始前保持 `baseline_readonly`。迁移审查必须先形成独立 Findings，再由架构方案引用，不能拿生成后的架构文档反向证明审查完整性。

## Phase 1: 全仓盘点

使用 `prompts/repository-auditor.agent.md` 分区审查，但保持只读。覆盖：

- 根目录、子包、模块边界、依赖方向和循环依赖；
- 源码、测试、脚本、生成物和重复实现；
- Prompt、Skill、Agent、Hook、MCP 与上下文契约；
- 根目录和嵌套 `AGENTS.md`、`CLAUDE.md`；
- README、docs、ADR、CONTRIBUTING 和示例；
- `.gitignore`、`.dockerignore`、包发布忽略文件；
- 环境变量、秘密、证书、令牌、样例配置和默认值；
- 包管理、锁文件、构建、格式化、Lint、类型检查和 pre-commit；
- 单元、集成、E2E、视觉、组件和性能测试；
- CI/CD、容器、部署、数据库迁移、可观测性和恢复；
- 前端组件、设计规范、状态管理、无障碍和响应式；
- 错误处理、日志、权限、隐私和供应链安全。

每个发现先在审查结果中分配稳定的 `AUD-NNN`，记录文件证据、影响、严重度、建议和可验证条件，不用个人偏好替代缺陷证据。Finding 必须来自旧项目或外部事实本身，不能引用尚未生成的迁移架构作为证据。

同时单独建立外部行为基线：用户实际输入、输出固定结构与语义、命令、路径、格式、公开 API、文件、错误行为和跨功能旅程。架构或技术栈迁移默认保持这些行为；只有用户明确确认的目标变化可以改变它们。

第一次全局架构确认前，Findings 只在对话中展示并保持目标项目只读。用户确认推荐架构方案后进入 `architecture_approved`，先使用 `templates/migration-findings.template.yaml` 将已展示的审查结果写入 `docs/架构迁移/审查发现.yaml`，再写迁移架构文档。后续任务与交付追踪以该独立文件中的 `AUD-NNN` 为权威审查输入。

## Phase 2: 外部参考调研

并行调用：

- `prompts/architecture-researcher.agent.md`；
- `prompts/competitor-researcher.agent.md`；
- `prompts/security-reviewer.agent.md`；
- 必要时 `prompts/test-engineer.agent.md`。

调研当前官方推荐、同类成熟产品、活跃开源项目和该技术生态的现代化工程实践。明确可直接借鉴、需要适配和不适合本项目的部分。

## Phase 3: 当前与目标架构比较

建立差距矩阵：

| 领域 | 当前证据 | 风险或成本 | 目标状态 | 迁移方式 | 验证 |
| ---- | -------- | ---------- | -------- | -------- | ---- |

至少覆盖：目录和模块、工具链、数据和接口、测试、安全与配置、文档与 Agent 指令、构建/CI/部署、UI 与组件、兼容性和回滚。

区分：必须修复、推荐改进、暂不处理、需要产品决策。每个需要实施的差距必须引用一个或多个 `AUD-NNN`；纯目标设计不得新造 Finding 来证明自身必要。

## Phase 4: 迁移方案

提出至少两个迁移策略，例如渐进式替换与集中重构。推荐方案必须说明：

- 迁移边界和不回滚的现有用户工作；
- 保持不变的产品行为和稳定接口；
- 目标目录树和依赖方向；
- 数据、配置、环境变量和秘密迁移；
- AGENTS/CLAUDE/README/忽略文件治理；
- 阶段顺序、兼容层、数据回滚与代码回滚；
- 每阶段可独立验证和提交的功能单元；
- 停止条件和失败恢复。

按用户可理解的功能域拆分迁移内容。全局迁移文档记录共同基线、目标架构、阶段和回滚；`docs/架构迁移/功能域/<功能域>.md` 记录本域边界、Findings、接口契约、验证和回退。

## Phase 5: 用户确认门禁

只在对话中展示独立审查摘要、候选方案和推荐迁移路径。用户确认前：

- 不创建 `docs/架构迁移/`；
- 不批量格式化；
- 不升级依赖；
- 不移动目录；
- 不修改代码、配置或文档。

用户确认后，先落盘 `审查发现.yaml`，再生成引用这些 Findings 的架构文档；不得颠倒顺序或从架构文档反推 Findings。
