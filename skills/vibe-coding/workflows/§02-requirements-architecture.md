# 需求包驱动的架构设计

适用于路线 1–3。

## Phase 1：建立需求与功能域矩阵

完整读取 `docs/产品需求/需求包清单.yaml` 和 `PRD需求文档.md`。先加载功能域索引，再按依赖顺序读取每个功能域的需求与行为样例。

为每个功能域记录：

- `F-NNN`、验收 ID 和行为样例 ID；
- 用户角色、入口、实际输入和输出，以及需求中确实存在的追问或状态；
- 输出语义和真实样例，以及需求中确实存在的固定结构或运行时可变内容；
- 必须保持的命令、路径、格式、公开 API、文件和兼容规则；
- 需求中明确的权限、响应、恢复、无障碍和安全要求；
- 直接依赖的输入输出契约。

只保持需求包明确要求的外部可观察行为。需求包未明确要求的旧模块、框架或数据库不是约束。

## Phase 2：按路线读取项目

- 路线 1：不读取旧项目，只读取目标目录中为保护用户工作所需的 Git 和规则事实。
- 路线 2：使用 `prompts/legacy-reference-inspector.agent.md` 派发独立只读 Agent，输入只包含用户授权路径与要回答的问题。返回结果必须是行为、输入、输出、公开契约、证据和证据缺口摘要；主 Agent 不把旧项目代码或架构原样注入架构讨论。
- 路线 3：读取当前项目的实现、测试、配置和文档，建立“已满足 / 缺失 / 冲突 / 明确变更”矩阵；现有实现仍不是产品意图的自动来源。

## Phase 3：并行只读调研

平台支持时按需调用 Architecture Researcher、Competitor Researcher、Test Engineer 和 Security Reviewer。优先读取官方一手来源，记录访问日期、版本与维护状态。

研究 Agent 不写文件、不安装依赖、不运行有副作用的命令，也不替用户做产品取舍。

## Phase 4：形成候选方案

提出确实可行的方案，比较会改变当前决策的系统边界、技术栈、目录与模块、数据和接口、验证、部署、成本和已证实风险。只有一个可行方案时，说明排除其他方案的事实依据，不凑备选数量。

全局方案说明共同技术与跨域依赖；每个功能域说明本域边界、组件、接口和验证策略。大项目不把所有域细节塞进一个文档。

推荐方案使用对应架构模板，覆盖项目路线、需求快照与参考边界、技术选择、目录依赖、跨域契约、环境与安全、验证顺序、风险和回退；不在本工作流重复维护模板字段清单。

提交第一次确认前，使用 `checklists/architecture-acceptance.md` 检查方案与需求、事实、边界和证据是否闭合；清单只处理无法由脚本判断的内容。

需求包含前端、GUI、TUI 或 CLI 时，完整读取 `../rules/ui-interaction-preview.md`。在对应功能域方案中复用需求包已经确认的全部可见状态和产品行为状态机，并补充实现所需的前后端边界、持久化、异步处理、失败回滚与模块调用。视觉风格可以优化，但不能擅自删除或改变已确认状态、操作、关键文案与转换。

## Phase 5：第一次全局确认

只在对话中展示推荐架构和备选差异，请用户一次确认架构、技术栈、目录、跨域边界、旧项目参考范围、兼容与部署边界、明确排除项。存在 UI 时，同一次确认必须包含受影响完整流程的可见状态和技术状态流；没有发生变化的已确认交互不在第二次任务确认中机械重复。

确认前不创建 `docs/架构设计/`，不搭建脚手架，不修改代码。功能域细节已经由需求包确认时不重复询问；发现真正缺失的产品决策时返回 `health-check` 的基线问题修复流程，不在架构阶段猜测。

第一次架构确认前允许的只读命令：`validate_prd.py` 与 `import_requirements.py` 的比较模式。
