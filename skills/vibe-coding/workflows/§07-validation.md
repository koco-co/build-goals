# 全链路验证与验收

可测量验收标准的唯一定义在 `rules/acceptance-standard.md`；本工作流只描述执行顺序。按需求、架构和项目事实选择适用项，结论记入 `checklists/final-acceptance.md`。

## Phase 1：需求和任务追踪

确认：

- 每个 `F-NNN` 和 `F-NNN-AC-NN` 都映射到至少一个任务和测试；
- 每个迁移高优先级发现都有处理结果；
- 每个任务都有 commit SHA、验证命令和最终状态；
- 没有用“基本完成”“大致支持”代替明确结果。

先按 `docs/产品需求/需求包清单.yaml` 的功能域逐域核对，再检查跨域用户旅程和直接依赖契约。阶段需求包只验收清单纳入范围，但必须验证其外部依赖契约。

## Phase 2：机械质量门禁

运行项目实际采用的格式、Lint、静态类型、依赖、构建、测试、迁移或安全检查。禁止通过删除测试、弱化断言、排除文件或关闭规则掩盖真实失败。

## Phase 3：正常测试数据

使用能覆盖对应验收场景的正常输入。只有需求涉及持久化、角色或多端状态时，才验证相应数据一致性；截图和报告不得泄露秘密或个人数据。

## Phase 4：UI 与交互条件分支

仅当项目存在前端、GUI、TUI 或可视组件时，验证需求明确的视口、状态、交互、视觉和无障碍要求。界面不得包含本次实现遗留的调试文本或模板占位符。

## Phase 5：归一化与仓库治理

核对项目实际存在的输入、输出、错误、状态、命名和公开契约是否使用同一权威定义；检查受本次变更影响的项目指令和文档，并确认没有已跟踪秘密或调试遗留。

## Phase 6：跨域端到端与独立复核

全部功能域通过本域门禁后，执行需求中存在的跨域用户旅程和直接依赖契约，并运行受本次变更影响的回归。调用独立 Reviewer（`prompts/reviewer.agent.md`）；只有项目存在对应要求时才调用 UI 或 Security Reviewer。Blocking Finding 修复后重跑受影响检查。

写入 `docs/交付验收/交付验收报告.md` 和各功能域交付文件后执行：

```bash
python3 <vibe-coding>/scripts/validate_delivery.py \
  <project-root> \
  --mode <greenfield|continuation|migration> \
  --phase delivery \
  --require-clean \
  --strict
```

该门禁会再次运行项目指令结构校验并枚举 Git worktrees；任务清单中已完成且已集成的任务如果仍登记着对应 worktree，将以 `COMPLETED_WORKTREE_REMAINS` 失败。阻塞、存在独有提交或未纳入本轮任务清单的 worktree 必须保留并在报告中解释，不得为通过校验而强制删除。

无法完成真实客户端、外部服务或生产等价验证时，标记为未验证，并说明缺少的证据和影响。
